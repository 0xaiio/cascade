## 二、功能详述（按主题，直接对应可拍摄镜头）

### 1. 字幕流水线：下载中英字幕 + 自动挂 B站 CC 字幕

**视频里怎么讲**：下载一个带字幕的视频，任务行直接出现「字幕」按钮；投稿到 B站 后，

字幕会被自动转成 B站 CC 字幕挂上去——不用再手动上传。

- **下载侧**（`subtitle_plan.py`，纯逻辑不联网）：
  - 按**主语言**判定要不要下字幕，依据是 yt-dlp 给原始语音 ASR 轨加的 `-orig` 后缀（平台信号，不是猜标题）；判不出退 `en`（有界默认），`yue` 不算中文。
  - 优先级：人工字幕优先，缺失才降级 ASR，都没有则跳过且不中断。
  - 结论按**磁盘证据**落库（yt-dlp 对「语言不存在」是静默跳过），`NULL`（没结论）与 `none`（结论是没有）分开处理。
- **上传侧**（`bili_subtitle.py` 新增 SRT/VTT→BCC 转换，`bili_api.save_subtitle`）：
  - `oid` 必须是 **cid**（不是 aid），布尔要发小写字面量，BCC 的 `from/to` 是秒。
  - 语言标识走**实测白名单**：`zh/en/zh-Hant/zh-TW/zh-HK/ja/ko/yue/fr`；需求常见的 `zh-CN`/`en-US` 平台直接拒（`code=79011`），按字面实现会让每单在视频已投出后失败。
  - 字幕三档状态**独立于**稿件状态、不进徽标；补救只重传字幕（`retry_upload` 走 `_reverify_work`），**绝不重投视频**。
- **一键打开字幕**（`f605650`）：点按钮用系统默认程序打开 `.vtt`/`.srt`，或弹系统「打开方式」窗口——不造编辑器清单，`WinError 1155`（后缀没人认领）才退成选择器；`mode=default|chooser` 用枚举而非布尔。
- **审核期字幕不再静默丢失**（`4420858`）：稿件进审核时 `cid` 为空、字幕无处可挂，旧逻辑记成 `skipped` 且只对 `failed` 开放补传 → 永久丢失；改为记 `failed` 并放宽补传判据到「有字幕文件且还没 `posted`」，并把 CC 字幕状态行**画到界面**上（此前这行渲染代码一直没进版本库）。
- **字幕结论不再报一个看不懂的数字**（`5ed7266`）：界面原来写「CC 字幕已上传（239 条，en）」。`239` 是 BCC 的段数（平台回读确认 239 条逐条一致，**不是**算错），但它既不是字数也不是句数（这份文件 122 句），旁边还跟着平台码 `en`。虚高的根因是滚动字幕的 **10 毫秒过渡条**没被丢掉（241 条 cue 里 119 条是它，旧的合并只认「整条同文」）。现在按「≤50ms 且文字被紧邻 cue 覆盖」丢弃（全语料 28 个字幕：20385 → 10973 条，丢的 100% ≤20ms，0 文字丢失），界面只说「CC 字幕已上传（英文），观众可在播放器里开关」。

**改动规模**：后端 +111 测试（928→1039 passed）；前端 `SubtitleOpenButton.tsx`（新增）、`biliStatus.ts`、`BiliJobStatus.tsx`；新增 `test_bili_subtitle.py`、`test_subtitle_plan.py`、`test_subtitle_recording.py`、`bili-subtitle-line.test.tsx`。

### 2. 任务完成提醒：提示音 + 右下角浮层

**视频里怎么讲**：勾一个「完成后通知」，任务跑完时——无论你在不在看——都会响一声提示音，

右下角弹出一个浮层告诉你哪个任务完成了。

- 之前这个开关**前后端完全没接线**：后端检索 `notify` 只命中字段定义一处，前端除开关外无任何消费点，文档甚至写着「不要据此期望系统通知」。
- **修好后**（`e74fddc`）：
  - 全局设置 `completion_notification`：`off / sound / toast / both`，**默认 `both`**；逐任务 `notify_on_complete` 决定「要不要」（默认 `false→true`，否则「在设置里选了方式」是空话）。
  - 提醒**在浏览器里发生**：提示音由 Web Audio **现场合成**（C6→G6，没有任何音频文件入库）；浮层是右下角 DOM，约 6s 自动缩回、悬停暂停、**标签页在后台时不倒计时**（否则后台等于没选）。
  - 触发条件是**状态跃迁**而非「当前状态」：必须比对上一次状态，否则会把「一进来就已跑完」的历史任务反复播报；`cancelled` 不算终态。
  - 非法取值（环境变量写错、落库值被改坏）一律收敛回 `both`，不让前端拿到不认识的值。

**改动规模**：前端 +19 用例（172→191），新增 `notifications.ts`（274 行）、`CompletionToasts.tsx`、`completion-notification.test.tsx`（284 行）；后端 +10 用例（913→923），新增 `test_completion_notification.py`（170 行）。

### 3. 进程重启恢复：关掉应用不丢任务

**视频里怎么讲**：下载到一半把应用关了，再打开——任务不会卡死，而是从断点**接着下**。

- 队列是内存里的 `asyncio.Queue`，进程一退，`queued/running` 条目的 id 就没了，库里状态却留着 → 一批永远不动、日志里连一行都没有的任务（生产库曾积 332 queued + 3 running）。
- **修好后**（`ead7b81`）：新增 `orphan_recovery.py`（只改条目状态）+ `JobManager.recover_orphaned_work()` 在 lifespan 里、`start()` **之前**执行（先改库再起 worker，消掉并发写库窗口）。
  - 默认策略 **resume**（重新排队 + 断点续传）：下载幂等可续传，重排队最坏只是多下一遍；而标记失败要用户逐条点「重启」才能恢复，正是这个缺陷的痛点。
  - `YTDL_ORPHAN_RECOVERY=fail` 是逃生阀；`paused` 条目任何策略下都不恢复；有已取消条目的任务视为「正在被取消」。
  - **真实设备验收**：只留一半 `.part`（16,346,981 字节）后重启，首帧进度从 16,348,005 起算——是真的续传而非重下；成品 32,693,962 字节与基准完全一致。

**改动规模**：新增 11 条用例（8 规则 + 3 走 TestClient lifespan 的端到端）；`orphan_recovery.py`（207 行）、`job_manager.py`(+138)、`db.py`(+20)、`test_orphan_recovery.py`（303 行）。

## 二·续：锚点（5ed7266）之后落地的打磨与修复（视频素材）

> 以下 10 个提交（`5ed7266..3dbcd83`）不新增能力大类，而是把阶段一已记录的「字幕打开 / 重试归集 / 上传进度」打磨成可用、可演示。制作新视频时，这些应作为「它现在真的好用了」的证据，而非新功能点。

### 1. 「打开字幕」按钮：一颗按钮，点开即弹选择器（ui/006 / ui/007）

- 提交 `2c5aafb`：原先是「主段 + 20px 下拉三角」的组合按钮，右段点下去没有任何可见反应（窗口被 `OpenWith.exe` 持有、留在浏览器后只在任务栏闪一下）。改为**只留一颗按钮**，点击即弹系统「打开方式」选择器（`mode` 缺省 `chooser`），tooltip 改为「打开字幕文件；可选择打开方式」。
- **视频里怎么讲**：点任务行的「字幕」按钮，直接弹出系统的「用哪个程序打开」——不用再找文件。

### 2. 「打开方式」对话框：三级降级链（bug-fix/023）

系统那套「打开方式」UI 在本机整体降级（实测 5 种标志位 × 3 种后缀一律只给 680×118 提示框，不是选择器），且 `SHOpenWithDialog` 失败得干干净净（窗口根本没创建，接口 204 却无从区分「做了」和「没做」）。演化（`cd4bb2d` → `8bdc96b` → `def9d40`）：

- 先试 `SHOpenWithDialog`（本进程内绘制，窗口高度 ≥ 300px 才算真选择器）；
- 否则 `OpenAs_RunDLL`（按 `OpenWith.exe` 认领）；
- 都不行时退到**应用自带 tkinter 对话框**：列出系统为该后缀登记的处理程序（注册表 `FileExts/OpenWithList` 等，只保留真实存在的 exe）+「浏览…」；本机候选实测含记事本/VS Code/CLion 等，写字板随 Win11 24H2 已移除。
- 任务行新增「正在打开…」提示（整条链 1~2s，沉默两秒等于「没反应」）；已有窗口时再点不叠第二个，并给出下一步说明。
- **视频里怎么讲**：点「打开方式」，系统给了程序清单就直接用；系统不给，应用自己弹一个带清单的对话框让你挑。

### 3. 「重试归集」：先回读平台补分P编号，再决定能不能归（bug-fix/024）

- 提交 `e1c43b9`：旧实现读库里那几行，稿件在审核时 `cid` 为空 → 这次「重试」**连一个请求都不发**（实测 22ms 返回同一句话），却仍回「已重新尝试归集」，合集永远停在「等待归集」。改为新增 `bili_upload.refresh_episode()`：**先按 bvid 认人**（标题可能被平台改写）、只读回读，读不到返回 None（不把 reviewing 降级成「待核对」），拿到 `cid` 后再归集。实测一次点击即从 `reviewing/-30` 变 `published/0` 并完成归集。
- **视频里怎么讲**：`waiting`（连请求都没发）与 `grouped`（已归集）/ `failed`（真失败）三种回执能区分开——不再把「什么都没做」报成成功。

### 4. 「重试归集」点击有反馈 + 上传进度秒表不再替平台计时（ui/007 / ui/008）

- 提交 `e03fbb0`：
  - 「重试归集」点击中按钮禁用并写「归集中…」，结束留 `上次重试 HH:MM:SS` 落款；回执按 `action` 分色调（grouped 绿对勾 / failed·waiting 走提示框）。根因之一是 `JobQueue` 用 `void` 回调吞掉 Promise，加载态帧宽 0ms、落款永不写；改回 `Promise<boolean>` 后实测 6/10 帧有加载态（修复前 0/10）。
  - 审核期「上传进度」曾替平台计时：`since` 双义（在跑=started_at / 跑完=finished_at）而秒表又按 `waiting` 推进 ⇒ 52 秒的上传显示成 `已提交 6:41:54`。拆成 `startedAt`/`finishedAt`（跑完终点必为 null），跑完给**定值**「上传用时 00:53」且不再推进；秒表只认 `running`。
- **视频里怎么讲**：点「重试归集」能看到它真的在转、转完有落款；审核中的任务，那个「已用时间」在跑完后定格成「上传用时 00:53」，不再疯狂跳到 6 小时。

### 1. 全部接口加超时兜底：挂住的请求不会永远转圈（bug-fix/025）

- 提交 `5c4511d`：`frontend/src/shared/api.ts` 的 `request()` 直接 `await fetch(...)`，而 **`fetch` 本身没有超时**。
  后端把连接接下来却不回话（后端卡死、DNS 挂起、代理黑洞、线程池打满）时，Promise 永不 settle ——
  界面停在「正在读取账号里的合集…」这类**永不消失**的提示上，不报错、不超时、不结束。
  此前仓库里只有一处兜底（`biliHealth.ts` 的 12 秒账号探测计时器），其余 **40 个调用点全裸**。
- 修复：抽一层「截止时间」抽象，60 秒看门狗超时后给一句**能照做的话**（不是「超时了」而是「请求卡住，可能原因 + 下一步」）。
  60 秒这个值是**量出来的**：服务端侧本来就有边界（B站 请求 20 s、打开方式窗口 6 s、cookie 库等待约 10 s），
  所以 60 s 不会误伤任何正常路径。
- **视频里怎么讲**：这是「以前会坏、现在不会了」的好例子 —— 拔网线、关后端，界面不再无限转圈，而是给一句能照做的提示。

### 2. 清晰度取值归一化并当场拒绝：不再「静默下最高画质」（bug-fix/026）

- 提交 `5d5b228`：用户把清晰度写成 `1440P`（或 `1080`、`hd`、`1440p60`）时，下载**不报错**，而是下**最高画质**。
  日志、界面、任务详情全都显示「正常」，用户唯一的发现途径是去看成品文件的分辨率。
- 修复：入口归一化 + 拒绝 —— 去空白、转小写，只接受 `best` 与 `<正整数>p`，其余返回 422 并在消息里点名三处可改的位置。
  归一化只做**无歧义**的改写：`1440P` → `1440p` 照做；`1080` / `hd` / `1440p60` **不猜**，直接拒绝
  （猜对九次没人夸，猜错一次就是「要 1080、实际下 2160」）。
- 一个容易漏的细节：设置里的「默认清晰度」走的是 `model_copy(update=…)`，**pydantic 不会重新校验** ——
  只在 `DownloadOptions` 上加校验，重启下载这条路会静默漏过去。三个入口都要单独挡。
- **视频里怎么讲**：把清晰度写成 `1080` 会被当场拦下并告诉你该写成什么，而不是「默默下了个 4K」。

### 3. SSE 断开即注销：关掉的标签页不留无界队列（bug-fix/027）

- 提交 `ba10f37`：`async for` **不会**关闭子异步生成器（PEP 525 的老坑）⇒ `EventBroker.subscribe()`
  的注销逻辑要等 GC 才跑。每关一个标签页就留一个订阅者，而 `publish()` 仍会逐个喂它，队列是无界的。
- 修复：显式持有订阅对象并在 `finally` 里 `aclose()`。注销判据仍收在 `subscribe()` 一处，路由层只负责「保证它被调用」。
- **视频里怎么讲**：不值得单独上镜头，属于「你反复开关页面时它不会越攒越慢」的隐形改进。

### 4. 两条内部质量修复（不进视频，但影响「能不能信这工具」）
