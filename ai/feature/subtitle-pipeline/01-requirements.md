# 需求：字幕下载与 B站 CC 字幕上传

适用读者：需要判断「这次改动是否符合当初要的东西」的人。实现细节在
[03-implementation.md](03-implementation.md)，技术选型理由在 [02-design.md](02-design.md)。

视频上传本身**不在本册范围内**（已实现，见
[ai/feature/bilibili-upload](../bilibili-upload/README.md)）。本册只讲挂在它上面的两段：
**下载时把字幕取下来**、**投稿后把字幕挂上去**。

## 原始需求

> 一、字幕下载（YouTube）
> 1. 只处理英文和中文字幕，忽略其他语种。
> 2. 按视频主语言决定下载目标：英文视频下载英文字幕，中文视频下载中文字幕。
> 3. 英文字幕优先级：优先下载官方/人工上传的英文字幕；不存在时降级下载机器自动生成（ASR）的
>    英文字幕；两者都没有则跳过下载，不中断流程。
> 4. 下载结果需记录字幕语言与来源类型（人工 / 自动生成），供上传环节使用。
>
> 二、B站 字幕上传
> 1. 在已有的视频上传流程中增加字幕自动上传环节：视频上传成功后，将已下载的字幕文件一并提交。
> 2. 上传的字幕必须为**可关闭的 CC 字幕**，B站 端允许用户自主选择是否显示，保证想看无字幕原片
>    的观众可以关闭。
> 3. 无可用字幕时（下载被跳过），仅跳过字幕上传，视频上传流程仍正常完成。
> 4. 处理好字幕格式转换、命名、语言标识（如 `zh-CN`、`en-US`）等细节。

「其余细节（日志、失败重试、异常提示等）请自行合理设计并实现」—— 自定的那部分在下面
「自行设计的细节」一节逐条列出，并说明理由。

## 需求逐条落点

| 编号 | 需求 | 落到哪 | 判据 |
| --- | --- | --- | --- |
| R-1 | 只处理中英，忽略其他语种 | [`language_family`](../../../backend/app/subtitle_plan.py#L109) 是**唯一**的族判定入口；界面列字幕与下载选语言共用同一份过滤（`YtDlpService._map_subtitles`） | 传入 `ja` / `ko` / `yue` 返回 `None`；`yue`（粤语）**不算**中文 |
| R-2 | 按主语言决定下载目标 | [`detect_primary_language`](../../../backend/app/subtitle_plan.py#L140) | 判据是 yt-dlp 的 `-orig` ASR 轨（平台标出的原始语音语言），不是标题/频道 |
| R-3 | 人工优先 → 降级 ASR → 跳过不中断 | [`resolve_subtitle_plan`](../../../backend/app/subtitle_plan.py#L200) + 把 `subtitleslangs` 收敛成一条 | 同一语言的人工轨存在时绝不选 ASR；都没有时 `origin=none` 且**下载照常完成** |
| R-4 | 记录语言与来源 | `JobItem.subtitle_language` / `subtitle_source` / `subtitle_path` | 来源是 `human` / `auto` / `none` 三值之一，不是「有没有」的布尔 |
| R-5 | 投稿成功后一并提交字幕 | [`_attach_subtitle`](../../../backend/app/bili_upload.py#L305)（`run_single` 的最后一步） | 必须在拿到 `aid` / `cid` 之后；拿不到就跳过 |
| R-6 | 必须是可关闭的 CC 字幕 | `POST /x/v2/dm/subtitle/draft/save`（[`save_subtitle`](../../../backend/app/bili_api.py#L366)），BCC 走 `oid=cid` | 字幕是**字幕轨**而非烧进画面；播放器里可关 |
| R-7 | 无字幕时只跳字幕、视频流程照完 | `SubtitleOutcome(state="skipped")` | 稿件状态**不因字幕而变**；`skipped` 是默认态 |
| R-8 | 格式转换 / 命名 / 语言标识 | [`bili_subtitle.py`](../../../backend/app/bili_subtitle.py)（SRT/VTT → BCC）+ [`find_subtitle_file`](../../../backend/app/output_paths.py#L162)（命名发现）+ [`bilibili_language`](../../../backend/app/bili_subtitle.py#L83)（标识） | 见下节的**一处与需求文字冲突的实测** |

## 一处与需求文字冲突的实测（重要）

需求第 4 条举的语言标识是 **`zh-CN` / `en-US`**，但**这两个值 B站 都不认**。用真实账号以
`submit=false`（只存草稿、不发布）逐个枚举，结果是：

| 值 | 平台响应 |
| --- | --- |
| `zh` / `en` / `zh-Hant` / `zh-TW` / `zh-HK` / `ja` / `ko` / `yue` / `fr` | 接受 |
| `zh-CN` / `en-US` / `zh-Hans` / `en-GB` | **拒绝**，`code=79011 不合法的语言` |

判据与复现脚本见 [04-testing.md](04-testing.md#语言白名单的实测依据)。因此实现里：

- `zh-Hans`（下载侧最常见的中文轨代码）→ `zh`；
- 繁体三档 `zh-Hant` / `zh-TW` / `zh-HK` **原样保留**（它们在白名单里，压成 `zh` 反而丢信息）；
- 英文一律 `en`；认不出来退 `en`（有界默认，不是随机）。

按需求文字原样实现 `zh-CN` 的后果是**每一单都在最后一步失败**，而且失败发生在视频已经投出去之后。
这一条按实测做，不按字面做，并在 [docs/api.md](../../../docs/api.md) 里写明。

## 自行设计的细节

需求留白了「日志 / 失败重试 / 异常提示」，以下是自定的那部分以及这么定的理由：

| 设计 | 决定 | 理由 |
| --- | --- | --- |
| **字幕失败不算投稿失败** | 字幕的三档状态（`posted` / `skipped` / `failed`）**独立于**稿件状态，绝不把 `published` 翻成 `failed` | 视频已经投出去了。把它标成失败会让用户去重投一遍 —— 那才是真的错 |
| **字幕失败有专门的补救动作** | 已发布/审核中且 `subtitle_state=failed` 的稿件，重试走**只重传字幕**（`_reverify_work` 带字幕参数），不再投一次视频 | 重投视频不可撤销；只重传字幕是幂等的 |
| **每条结论都带一句人话** | `subtitle_message` 恒非空（成功也写） | 「没字幕」和「字幕传失败了」看起来一样，不给一句话用户无从区分 |
| **落库按磁盘证据，不按计划** | `_record_subtitle_result` 用**文件是否真的在磁盘上**判定 | yt-dlp 对「请求的语言不存在」静默跳过、不报错，所以「计划说有」≠「写出来了」 |
| **`NULL` 与 `none` 分开** | `subtitle_source=NULL` = 这一轮还没有来源结论；`none` = 有结论（没有可用字幕） | 混成一句会让用户刚提交任务就看到「无字幕」 |
| **投稿表单里预告字幕** | `BiliPrefillItem.subtitle`（如 `en · 人工`、`无字幕`）由**服务端**拼好 | 前端自己拼一遍就会出现「界面写自动生成、后端写 ASR」两套说法 |
| **重跑清掉旧结论** | 条目每次开跑前把三列重置 | 上一次留下的 `subtitle_path` 指向可能已被删掉的文件 |
| **字幕日志有独立前缀** | `bili 字幕上传完成：bvid=… lan=… 条数=…` / `bili 字幕转换失败：file=…` | 与 `biliup 输出 | ` 那条通道分开，排查时能一眼分清是投稿还是字幕 |

## 不做（明确排除）

| 不做 | 理由 |
| --- | --- |
| 处理中文/英文之外的语种 | R-1 明确要求。界面也不再列出其它语种（两处真相会让用户选了却下不下来） |
| 下载**多**条字幕（例如中英各一份） | 需求是「按主语言决定下载目标」，单条。多条会让上传环节不知道该传哪一份 |
| 一次投稿挂多条字幕轨 | 平台一次 `save` 是一轨；挂两条要两次调用并各自记录状态，本轮不做 |
| 把字幕烧进画面（硬字幕） | 与 R-6 直接冲突：硬字幕关不掉 |
| 自动翻译字幕 | 平台侧能力，且会改变字幕语言；不在需求内 |
| ASR 缺失时改用界面上的人工翻译 | 无翻译能力，也不是「下载」 |

## 凭什么算做完

1. 一个**英文**、只有 ASR 英文轨、没有任何人工字幕的视频：下载完成，记录
   `subtitle_language=en`、`subtitle_source=auto`，且磁盘上有 `.en.srt`（或对应轨名的）文件。
2. 一个**中文**、同时有人工 `zh-Hans` 与 ASR `zh-Hans-orig` 的视频：记录 `human`，**不会**同时
   落下两份中文字幕。
3. 一个**只有日文字幕**的视频：视频下载照常成功，三列落成「没有可用字幕」，**不报错、不中断**。
4. 上述 1/2 的产物投稿后：B站 播放器里出现字幕开关，且默认是**可关**的；稿件状态是「已上传」。
5. 上述 3 的投稿：稿件正常发布，字幕一栏显示「已跳过」，稿件状态**不受影响**。
6. `zh-Hans` 的字幕传到 B站 后语言标识是 `zh`（不是 `zh-CN`），且接口返回 `code=0`。

自动测试与手工验收步骤见 [04-testing.md](04-testing.md)。

## 增量：打开字幕文件（2026-10-18 下午）

> **后续变更（2026-10-21）**：本节的「主段 + 右段挑程序」已收成**一颗按钮**——点它就是弹系统的
> 「打开方式」（tooltip「打开字幕文件；可选择打开方式」）。理由与实测见
> [ui/006](../../ui/006-the-subtitle-arrow-looks-dead.md)。原始要求原文保留如下，不再追改。

原始要求（用户原话要点）：「下载任务中心的每个视频条目上新增一个『打开字幕』按钮……位于『打开视频
所在文件夹』按钮的右侧；点击后可直接调用系统默认编辑器或文本查看器打开字幕文件，也可弹出窗口让用户
选择使用哪个查看器或编辑器打开该字幕文件，并支持记住上一次使用的查看器或编辑器。由于该打开文件功能
在多处场景通用，请按最标准的通用实现方式完成，避免重复造轮子。UI 层面，该按钮需清晰、对用户友好，
使用户一望即知其功能为打开字幕文件；鼠标悬停时显示 Tooltip，内容为『打开字幕文件』。」

| 要求 | 落点 |
| --- | --- |
| 每个视频条目都有按钮，位于「打开视频所在文件夹」右侧 | 单视频任务行与 playlist 条目行各一处，紧跟在文件夹按钮之后 |
| 直接调用系统默认程序打开 | `mode=default` → `os.startfile`（mac/linux 走 `open` / `xdg-open`） |
| 也可弹窗让用户挑程序 | `mode=chooser` → 系统的「打开方式」窗口（shell 的 `OpenAs_RunDLL` 入口） |
| 记住上一次使用的查看器 | 由**系统**记：窗口里勾「始终使用此应用」即改该后缀的关联，下次主按钮直接生效 |
| 按最标准的通用方式、不重复造轮子 | 通用能力落在 `system_open`（已有的「本机打开」模块），不新开一个「文件打开器」；不维护编辑器清单 |
| 一望即知 + Tooltip「打开字幕文件」 | 字幕图标（`Captions`，即 CC）+ `title="打开字幕文件"`；右段小箭头 `title="选择打开方式"` |

**自行设计的细节**：

- **没字幕的条目按钮置灰**，`title` 改成「字幕文件尚不可用」。可点性只看读模型给的 `subtitle_path`
  （真的存在才给值），因此界面上不存在「点得下去但必然 409」的按钮。
- **`mode` 是枚举而不是布尔**：`default` / `chooser`，别的值一律 `422`。布尔会随「再加一种打开方式」
  立刻变成两个布尔参数。
- **没有关联不是错误**：Windows 上该后缀还没人认领时（`WinError 1155`），默认模式自动改弹选择器，
  其它错误照原样抛。
- 失败文案就近显示在那一行（与播放/打开文件夹同一条通道），不进全局提示区。

**不做**：

1. **不做编辑器清单**（notepad / VS Code / Sublime…）。它只能是系统处理器注册表的子集，用户装了什么
   我们无从得知，还得为每个平台各维护一份。
2. **不在应用侧存「上次用的查看器」**。系统已经在 `FileExts\<ext>\UserChoice` 里记了一份；再存一份，
   两份结论迟早打架，而用户无法判断该信谁。
3. **不接收前端传路径**、不把字幕内容读出来在界面里预览（那是另一个功能）。

**凭什么算做完**：见 [04-testing.md](04-testing.md) 的「增量测试」与手工验收第 12a 步 ——
其中「勾了始终使用之后，再点主段是同一个程序」是唯一能证明「记住」真的成立的验收。
