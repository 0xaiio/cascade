# 设计：字幕翻译

## 一、分层与落点

| 层 | 模块 | 职责 | 不做什么 |
| --- | --- | --- | --- |
| L3 | `translation/align` | 解析、分块、序号回填、对齐校验、中文断行 | 不发请求、不写文件、不改时间 |
| L3 | `translation/provider` | 契约与类型化回复 | 不做 HTTP |
| L3 | `translation/local` | 本机 OpenAI 兼容 HTTP、错误分类、loopback 校验 | 不重试、不读库 |
| L3 | `translation/store` / `render` | JSON 原子写 / SRT 渲染 | 不翻译、不决定业务状态 |
| L2 | `translation/service` | 后台编排、进度、取消、重试、导出 | 不写 HTTP 状态码 |
| L0 | `api/routers/translation` | 9 条路由 | 不做业务规则 |
| 前端 | `translation/` | 抽屉、API 封装、两个入口 | 不算进度、不拼字幕路径 |

## 二、为什么"时间轴不属于翻译"

译文只是原文每条的属性。代码里**没有写 `start`/`end` 的路径**，`AlignedCue` 的时间只从源
`Cue` 复制。导出前 `validate_alignment` 再逐值检查一次。这是结构性保证，不靠用例碰巧守住。

## 三、为什么整块拒绝而不是尽量回填

模型把第 3 条译文写成第 4 条时，文件仍是合法 SRT、时间也合法，用户看到的是整段错字幕 ——
而且没有任何报错。所以序号集合不一致就整块拒绝。唯一的例外是**合法子集的漏条**：
只补问缺失编号，得到后用完整集合重新校验；绝不猜一个序号填进去。

## 四、为什么逐条数据在 JSON、DB 只存索引

编辑是逐条高频动作；JSON 可以同目录临时文件 + `os.replace` 原子替换，进程被杀也只会
留下旧版或新版。DB 再存一份逐条数据就会出现两处真相（"刷新后看到旧译文"）。

## 五、为什么只补失败块、且锁定人工修订

- 重试若把已译条目再发一次模型，既费时又可能把好译文改坏；只补 `failed` / `pending`。
- 用户改过的译文是最终决定，机器重跑不能覆盖；`edited` 条目连请求都不发。

## 六、B站 双轨

`lan=en` 与 `lan=zh` 是两条独立 CC 字幕（同 `lan` 才覆盖）。稿件已投稿时补译轨走
"只补字幕"路径（`reverify` 语义），不跑投稿命令，`aid`/`bvid` 不变。
译轨结论与原轨分开三列，避免"en 成功"掩盖"zh 失败"。

## 七、被否决的方案

| 方案 | 为什么不选 |
| --- | --- |
| 外部翻译 API | 用户要求仅本地模型；且会把用户字幕发给第三方 |
| 新建编辑器/模型清单 | 本机 `llama-server` 已是 OpenAI 兼容，换模型只改地址与名字 |
| 合并滚动重复条后再翻译 | 会破坏"逐条对齐"；合并只属于 BCC 导出那条路径 |
| 前端自己算序号/时间 | 与后端两处真相；前端只显示后端给的数据 |

### 增量设计：为什么同屏不是两条轨

`en` + `zh` 两条 CC 轨在播放器里是切换关系；要同屏，必须一条 cue 两行文本。
`bilingual_content(source, translation)` 默认英上中下，两边各自把内部换行压成空格，
确保只显示两行；`to_bcc_entries` 是 BCC 结构的唯一来源。
模式只改呈现与导出，不改译文、时间轴、已上传的单语轨。

被否决：让前端把两条轨叠在一起（播放器不支持）；为双语另写一份 BCC 结构（必漂移）。

### 增量设计：谁负责让模型服务可用

早先的设计把"先启动 llama-server"写成用户的一次性准备步骤，实测这就是一个必然失败的入口：
机器重启或关过一次服务后，按钮只会回一句 `WinError 10061`。现在把这件事收回应用侧：
翻译编排在发请求前确保服务可用，健康则复用，否则按需拉起。边界仍是只连 loopback、
只执行 PATH 中的二进制、不用 `shell=True`、不下载模型；失败时**不发请求**并给可操作结论。
进程 detached 是为了让它独立于应用存活，下次点翻译直接复用。
