# 字幕翻译：非中文字幕 → 中文字幕

- 状态：**已实现**（2026-11-17，按 [plan.md](../../plan/plan.md) §10 分五步落地，每步独立验收与提交）
- 提交：步骤 1 `346dbe9` / 步骤 2 `6da3b7c` / 步骤 3 `7ad29e7` / 步骤 4 `7606085` / 步骤 5 本次
- 入口：任务中心「打开字幕」按钮旁，以及 B站 投稿预览表「字幕」列

## 一句话结论

把已下载的非中文字幕**逐条**翻译为简体中文：原文只读、时间轴逐值复制、译文可人工修订；
导出纯中文轨与原上译下的对照轨；可把中文作为**独立 `zh` CC 轨**挂到已投稿的 B站 稿件上，
与原 `en` 轨并存、观众可关。当前阶段只连**本机模型**，运行时不新增依赖。

## 三步链

1. `align`：SRT/VTT 解析（复用 `bili_subtitle`）→ 8 条/1200 字符分块 → 序号回填与整块校验。
2. `local`：OpenAI 兼容 HTTP（标准库 `urllib`）→ 本机 `Qwen3-8B-Q5_K_M`，只接受 loopback。
3. `service`：后台分块、逐条 JSON 原子写、SSE 进度、人工修订锁定、只补失败块、导出与补挂 `zh` 轨。

## 五条判据（比"翻得准"更可验证）

| 判据 | 落点 |
| --- | --- |
| 译文条数 = 原文条数，index 一一对应 | `apply_chunk` 的序号集合校验，错位整块拒绝 |
| `start` / `end` 逐值相等 | `AlignedCue` 没有写时间的路径；`validate_alignment` 导出前再挡一次 |
| 原字幕不被改写 | 只读 + SHA-256 记录；导出写新文件 |
| 人工修订不被机器覆盖 | `edited` 锁定，重跑连请求都不发那条 |
| B站 双轨并存、不重投视频 | `lan=en` / `lan=zh` 两条 CC 轨；补挂只走"只补字幕"路径 |

## 为什么只支持本机模型

用户要求"当前阶段仅支持本地模型；选择翻译质量尽可能高的本地模型；允许自行下载安装模型，
但运行时不新增依赖"。本机条件：`llama-server`（MSYS2 UCRT64）+ RTX 5070 Laptop 8GB。
选 `Qwen3-8B-Q5_K_M`（5.85GB，Q5 在 8GB 显存内可全量驻留，中英技术字幕质量明显优于 4B/1.5B）。
协议选 OpenAI 兼容的 `/v1/chat/completions`，HTTP 用标准库 —— 换模型只改地址与模型名。

**外部 URL 在设置接口和 provider 构造处双重拒绝**：字幕文本是用户内容，不能悄悄发到第三方。
界面没有 API Key 字段，契约里也没有。

## 实测边界

- 本机 8B 生成约 **3.8 token/s**（Vulkan 后端也未显著加速）。故分块 8 条、单请求超时 300 秒；
  长片是分钟级任务，界面按条推进度而不是百分比。
- 模型偶发漏 1 条或空译文：合法子集只补问缺失编号，不猜序号；反复失败标 `failed` 可重试。
- "观众能关"与"双轨在播放器里可见"属于平台行为，未在真实 B站 账号上端到端确认。
- 详细设计与取舍见 [02-design](02-design.md)、实现见 [03-implementation](03-implementation.md)、
  验收见 [04-testing](04-testing.md)。

## 增量：中英双语同屏（2026-11-17）

提交：`2f15b71`（纯渲染）→ `d33b80a`（模式与导出）→ `cec696f`（上传）→ 本次（文档）。

用户确认了两个默认：**英上中下**、**保留 `en`+`zh` 单语轨供切换，双语只是第三种呈现**。
核心判据：B站 一次只显示一条轨，同屏必须把两行放进**同一条 cue 的 `content`**；
两行共用唯一 `from`/`to`，结构上不可能不同步。BCC 结构仍只有 `to_bcc_entries` 一处。
切换呈现不重译，但必须重新导出后才能上传（同 `lan` 覆盖，不是新增轨）。

## 增量：本机模型服务按需启动（2026-11-17，缺陷 041）

翻译入口不再依赖用户预先手动跑 `llama-server`：`translation/model_server` 在发请求前探 `/health`，
不通就用 PATH 中的可执行文件与本机已有 GGUF 拉起，Vulkan 失败回退 CPU；失败时零请求、给一句可操作结论。
"用户不该先做什么才能让按钮工作"是这次的核心判据 —— 与上一轮"打开文件"交给系统的思路同源。

## 增量：字幕上传闭环（2026-11-17）

六项需求合成一条闭环：翻译完就能传、重启后不重译且入口变「打开中文字幕」、
投稿页三档字幕勾选默认全勾、等 cid 后按勾选补传且缺译文现场制作、投稿页移除手动翻译入口。
核心判断：**勾选要落库**（补传发生在几分钟后的另一次请求），**制作能力要注入**
（`BiliManager` 不该认识 `TranslationService`），**状态复用的判据是 provider 零调用**。
