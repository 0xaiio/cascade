# 007 · 「重试归集」点下去，按钮、那一行、页顶都没有任何一处变化

## 问题

合集行显示「等待归集 · 视频还在 B站 排队审核」并给出一颗「重试归集」。点它：

- 按钮**文字不变、不禁用**，一闪都不闪；
- 合集那一行的文案**一个字都不变**；
- 页顶也没有任何回执出现在视野里。

用户据此判断「这个按钮没实现」。原话：*「点击「重试归集」按钮后没有任何反应」*。

## 原因

四件事叠在一起，前两件让「没反应」成为**事实**，后两件让它**无法被排除**。

### 1. 那一下真的什么都没发生（功能侧，见 [024](../bug-fix/024-retry-grouping-never-asks-the-platform.md)）

视频还在审核 ⇒ 库里 `cid` 为空 ⇒ 归集没有可加的稿件 ⇒ 服务端在 22 毫秒内回同一句话。
**没有新事实，就没有可以变化的东西。**

### 2. 唯一的反馈在视口外

回执走的是页顶那条 `.notice`（在 `.grid` 之上、整页最上方）。用 CDP 量（1440×1000，卡片滚到视口中央）：

```
卡片 .job-card        top = 286   bottom = 713     visible = true
按钮 .bili-retry      top = 581   bottom = 611     visible = true
回执 .notice          top = -1115 bottom = -1069   visible = false     ← 在视口上方 1115px
```

用户盯着按钮，回执在**一千多像素之外**。而且它说的是「已重新尝试归集」—— 与行里那句
「等几分钟后点重试」自相矛盾，绿色的对勾还替它作证（配色见第 4 点）。

### 3. 加载态被 `void` 吞掉了（写用例时才发现的第二个原因）

组件里 `await onRetrySeason(...)` 拿返回值决定要不要写落款，而 `JobQueue` 把它接成了

```tsx
onBiliRetrySeason={(seasonRecordId) => void handleBiliRetrySeason(seasonRecordId)}
```

`void` 把 Promise 丢掉 ⇒ `await undefined` 立刻返回 ⇒ 「归集中…」的帧宽度是 **0 毫秒**、
落款永远不写。换句话说：**即使请求真的在跑，界面上也不会留下任何痕迹。**

### 4. 回执的配色只认「有没有回执」，不认「做成了没有」

`.notice` 是「已开始 / 已完成」那一档的绿底 + 对勾。而 `waiting` 的内容是「什么都没发」，
`failed` 是「又失败了」—— 三者共用同一个绿对勾，等于告诉用户「好了」。

## 修复方案

### 原地留下两件可观察的东西（`BiliJobStatus`）

1. **加载态**：点击后按钮变「归集中…」并 `disabled`（真实后端要回读平台，这一下是几百毫秒到几秒）。
2. **落款**：结束后在按钮右边写 `上次重试 12:34:56`（`font-variant-numeric: tabular-nums`，
   秒数跳动时右边缘不抖）。前提不满足时行内文案不变，这一格是**唯一**能证明「这一下真的跑了」的东西。
   请求本身挂了**不写落款** —— 落款的意思是「跑完了」，不是「我点了」（错误另有 `.alert` 那条通道）。

这两件事的时序靠一个**必须传出去的 Promise**：`onRetrySeason: (id) => Promise<boolean>`，
`JobQueue` 不再用 `void` 包一层，`App` 返回「这一下是否跑完」（`runBiliRetry` 也改成返回 boolean）。
第 3 条根因就是在这里被修掉的。

### 回执分色调

`biliNotice` 从 `string | null` 变成 `{ text, tone }`，`showBiliNotice(text, tone)` 是唯一写入口。
`action === "grouped"` 才用 `ok`（绿对勾），`waiting` / `failed` 用 `info`（`<Info>` 图标 + 蓝底 `.notice.is-info`）。

为什么不是「弹个 toast」：toast 解决的是「我知道它跑了」，解决不了「结论是什么、什么时候跑的」；
落款同时回答后两问，而这正是 [004](004-the-recheck-button-looks-dead.md) 验证过的那套。

## 效果

真实浏览器（`tmp_acceptance/probe_retry_grouping.py`，同一台机、同一条 Ep 125 记录）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 点击过程中 | 0/10 帧有变化（`重试归集` / `disabled=false`） | **6/10 帧**「归集中…」+ `disabled=true` |
| 点击结束后 | 行内文字全等，没有落款 | 按钮旁出现 `上次重试 01:30:56` |
| 回执 | 绿对勾「已重新尝试归集」，top = **-1115px** | `.notice is-info`「这次没有发起归集：视频还在 B站 排队审核…」 |
| 前提满足时 | 行内无变化（点击等于空转） | 行内直接变成「已提交归集（B站 需人工审核）」+ 稿件转「已发布」 |

## 验证

| 用例 | 钉住什么 |
| --- | --- |
| `「重试归集」在前提不满足时也要在原地留下痕迹：加载态 + 落款 + 说实话的回执` | 点击后按钮禁用并写「归集中…」→ 结束后落款匹配 `^上次重试 \d\d:\d\d:\d\d$`、按钮恢复可点、回执落在 `.notice.is-info` 且说「这次没有发起归集」 |
| `lets a failed collection be regrouped on its own`（既有，回归） | 成功那档照旧弹「已重新归集。」，按钮与请求都没被加载态挡住 |
| 探针 `probe_retry_grouping.py`（12 条读数） | 真实布局里按钮与回执的**坐标**、10 帧采样里的加载态、落款的真实文本 |

**承重测试**：把 `JobQueue` 的 `onBiliRetrySeason={onBiliRetrySeason}` 改回
`(id) => void onRetrySeason(id)`，新用例立刻卡在第一次断言：

```
Unable to find role="button" and name "归集中…"
（实际 100 ms 后按钮仍是「重试归集」，落款始终为 null）
```

这正是第 3 条根因的复现路径，不是「代码看起来对」。

## 风险与回滚

- `onRetrySeason` 的返回类型从严（`void` → `Promise<boolean>`）：**任何新调用方都必须把 Promise 传出去**，
  否则加载态与落款会静默失效。这是本轮唯一的接口收紧，`tsc` 会拦住漏改的地方。
- 落款用的是浏览器本地时间（`toLocaleTimeString("zh-CN", {hour12:false})`），跨语言环境下格式可能不同；
  用例只断言形状。
- 多了一档 `.notice.is-info` 配色，只影响 B站 区回执，不动 `.alert`。
- 回滚：`git revert <commit>`。

## 未覆盖 / 如实说明

- **成功后回执可能被徽标播报覆盖**：归集成功会让徽标从「上传中」翻到「已上传」，那条「跑完了」的
  播报（既有逻辑）会盖掉「已重新尝试归集」。两条都真、行内变化也明确，本轮**没有做优先级仲裁**。
- 「回执在视口外」这件事只有探针量到（jsdom 不做布局），单测无法覆盖；单测覆盖的是「按钮旁有落款」。
- 落款在**页面停留期间**不持久：切走再回来（组件重挂）就没了。它不是历史记录，只是「刚刚那一下」的凭据。
