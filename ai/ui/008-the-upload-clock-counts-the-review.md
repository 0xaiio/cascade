# 008 · 稿件在「审核中」，而「上传进度」的秒表还在往上数（一直数到 6 小时 41 分）

## 问题

`C++ Weekly - Ep 125` 投上去之后，任务卡片里一直挂着这块：

```
上传进度                                            已提交 6:41:18
━━━━━━━━━━  ━━━━━━━━━━  ━━━━━━━━━━  ━━━━━━━━━━
排队        传输        提交        核对
已提交，B 站 审核中
```

那次上传**实际只用了 52 秒**。数字却是一条只会往上走的钟，隔两秒读一次就涨两秒：

```
[1] 点之前       clock = "已提交 6:41:54"
[2] 2.6 秒之后   clock = "已提交 6:41:56"      ← 还在走
```

用户的原话：*「上传进度仍在持续计时」*。而它的标题写着「上传进度」—— 任何读它的人都会认为
**还有东西在传**。

## 原因

两个决定各自都说得通，叠起来就变成撒谎。

### 1. `since` 是一个双义值

`jobUploadProgress()` 返回的 `since` 在「在跑」时是 `started_at`、跑完之后换成 `finished_at`
（[020](../bug-fix/020-the-progress-clock-is-eight-hours-off.md) 为了让审核期的秒表不冻结而改的）。
同一个字段在不同档位代表**两个不同的时刻**，`uploadElapsedLabel(view, now)` 再拿 `now - since`
去算 —— 于是审核期算出来的不是「上传用了多久」，是「**从提交到现在过了多久**」。

### 2. 推进条件是「在等」，不是「在跑」

`BiliUploadProgress` 的 `useEffect` 依赖 `waiting`（在跑 **或** 审核中），每秒 `setNow`。
两者合起来：审核期的数字每秒 +1，而它量的是**平台的排队时间**。

020 当初这么改是有理由的：切到审核那一刻 `running` 变 `false`，秒表停在最后一个 tick 上
（`7:59:59`），「停住的时钟会被读成卡住了」。那个担心是对的，**但它选错了要表达的东西** ——
「卡住」与「已提交 52 秒」的区别不在数字动不动，而在**措辞**。

## 修复方案

### 1. 拆成两个端点，不再给双义值

`JobUploadProgressView` 的 `since` 换成 `startedAt` / `finishedAt` 两个字段；
**在跑时 `finishedAt` 必须为 `null`**（库里那一列可能留着上一轮的时间，拿它算会得出 0 或负数 ——
一个假的「上传用时」比不显示更糟）。

### 2. 措辞按「这一段结束了没有」分档

| 状态 | 文案 | 是否按秒推进 |
| --- | --- | --- |
| 排队 / 传输 / 提交 / 核对（在跑） | `已用 01:07` | 是（起点 = `started_at`） |
| 审核中（settled） | `上传用时 00:53` | **否**，定值 = `finished_at − started_at` |

`上传用时` 是个**已经发生完**的时长，读起来不像一个还在走的钟 —— 020 担心的「停住 = 卡住」由措辞解决，
而不是由「一直数下去」解决。四段轨迹本身在审核期全部 `is-done`、也没有 `is-active` 动画，
两块信息一起说的是同一件事：我们这一步做完了，现在等平台。

### 3. 秒表只认 `running`

`useEffect` 的依赖从 `waiting` 换成 `running`（`const ticking = view?.running ?? false`）。
「要不要渲染这块」仍然由 `waiting` 决定，两件事分开。

## 效果

同一条记录、同一个浏览器（探针 `probe_retry_grouping.py`）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| t0 | `已提交 6:41:54` | `上传用时 00:53` |
| t0 + 2.6 s | `已提交 6:41:56`（变了） | `上传用时 00:53`（不变） |
| 与服务端 `elapsed_seconds = 52` 的关系 | 差 6 小时 41 分 | 差 1 秒（四舍五入） |

## 验证

| 用例 | 钉住什么 |
| --- | --- |
| `等审核时给的是**定值**：上传用时 = 终点 − 起点，与此刻几点无关` | 同一份数据喂两个不同的 `now`，输出**必须相同** |
| `跑完却没有终点 → 不显示，也不拿此刻顶上` | `finished_at` 为空时返回 `null`，不是 `now - started` |
| `真实样本：Ep 125 那条（52 秒）…` | 真实时间戳 ⇒ `上传用时 00:5[23]`，且**不是**三段式（旧的 6 小时形状） |
| `审核中：秒表停在「上传用时」上，不再替平台审核计时` | 渲染 2.2 秒后仍是 `上传用时 00:00`，页面上没有 `已提交 \d` |
| `审核中：四个节点走完，明说没有百分比可读` | 同一档位的轨迹断言（既有，改文案后回归） |

**承重测试**：把 `uploadElapsedLabel` 的「跑完」分支改回 `now - started`（即修复前的算法），
三条转红：

```
× 等审核时给的是**定值**…
× 等审核时也一样：naive 时间戳按 UTC 算…
× 审核中：四个节点走完，明说没有百分比可读
3 failed | 3 passed
```

（组件那条 `秒表停在…` 在承重注入下仍绿，因为它钉的是**推进条件**而不是算法：`running` 为假时
组件根本不重渲染，`now` 停在首帧 —— 两条用例各钉一半，缺一条都留缺口。）

回归：前端全量 `282 passed`，`tsc --noEmit` 干净。

## 风险与回滚

- 审核期不再有「活着的数字」。如果哪天平台侧卡住几个小时，界面不会用滚动数字暗示「还在动」——
  但它会明说「已提交，B 站 审核中」，那是事实。
- `since` 字段被删除：**只有本组件消费它**（全仓库检索 `\.since\b` 无其它调用点），
  用例同步改写，无外部契约影响（它不在 API 里）。
- 回滚：`git revert <commit>`。

## 未覆盖 / 如实说明

- **本轮没有跑一次真实上传**来观察「在跑」那一档的秒表（那需要再投一条稿）。`已用` 分支的凭据是
  单测 + 修复前的探针读数（旧版在 `uploading` 下确实每秒 +1）。
- 传输那一段可能长达 481 秒（实测），「已用」在此期间仍是唯一的活性信号 —— 这条行为**没有变**。
- 时长按秒四舍五入：`52.55 s` 显示 `00:53`，服务端 `elapsed_seconds` 是 `52`（截断）。
  两处口径差 1 秒，本轮没统一（统一要动服务端的算法，属于另一处改动的范围）。
