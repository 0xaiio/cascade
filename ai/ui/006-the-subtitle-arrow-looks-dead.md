# 006 · 「打开字幕」右侧的下拉箭头点下去没有任何反应

| | |
| --- | --- |
| 发现于 | 2026-10-21，手工点击任务中心的「打开字幕」 |
| 影响面 | 任务中心每一行有字幕的条目（单视频任务行 + playlist 子视频行） |
| 性质 | 交互设计缺陷 + 一处置前的实现 bug（两者叠加才表现成「没反应」） |
| 提交 | 本次 |

> **后续变更（2026-10-21 深夜）**：本条里「按进程名认领窗口」的修法**已被取代**。真机复测发现
> 那次量到的是「窗口在后面」，而更常见的情形是**窗口根本没被创建** —— `OpenAs_RunDLL` 请的
> explorer 托管弹层失效时，调用返回 0 却什么都不弹。现在改用 `SHOpenWithDialog` 在本进程内画
> 对话框，并**弹不出来就报错**；`process_name` / `_process_image_name` 一并删除。
> 见 [bug-fix/023](../bug-fix/023-the-open-with-dialog-that-never-opened.md)。下面「原因」与
> 「效果」两节保留当时的实测记录，不再改写。

## 问题

界面上一颗按钮被拆成了两段：左边是字幕图标（CC），右边挨着一个 20px 宽的下拉三角。
点左边会打开文件；点右边那个三角 —— **什么都不会发生**：没有窗口、没有报错、没有提示，
只有任务栏里闪了一下。

用户能观察到的完整现象是「点了没反应」，而不是「弹了个窗口在背后」。这句话的差别决定了
修哪里：如果只是窗口没置前，那么等待 1 秒左右它会自己浮上来；实测是**一直不浮上来**，
必须先去任务栏找到那个窗口、再点一次才看得见 —— 也就是说，「点一下」这个交互从头到尾
没有完成过一次。

几何证据（1440×1000 视口，探针 `tmp_acceptance/ui_subtitle_button.py` 的前身量到）：

| 元素 | 宽度 | 位置 |
| --- | --- | --- |
| 「打开视频文件夹」 | 36.0px | `right = 683.0` |
| 「打开字幕」主段 | 36.0px | `left = 691.0`（间距 8.0px） |
| 右侧下拉箭头 | 20.0px（样式源文 `.split-button-toggle { width: 20px }`） | 紧贴主段右边，中间无缝隙 |

这段 56px 宽的组合控件里，有 20px 是一个**看不见效果的按钮**。

## 原因

两层原因，缺一层都不会是现在这个症状。

### 一、界面层：一个动作被拆成了两颗按钮

`SubtitleOpenButton` 当时是两个 `<button>` 套在 `.split-button` 里：主段 `mode=default`、
右段 `mode=chooser`。设计初衷是「换一个程序打开」这件事应该有独立入口，而 Shift 点击
这类修饰键在界面上看不见。问题在于：**右段的效果不是「换了个界面」，而是「桌面上多了一个
窗口」** —— 它需要被置前，才谈得上被看见。

### 二、实现层：置前逻辑按「谁被 Popen 起来」认领窗口，而窗口不归那个 pid

`open_path_with_chooser` 用 `Popen(["rundll32.exe", "shell32.dll,OpenAs_RunDLL", path])`
弹选择器，然后调 `_bring_windows_window_to_front(process.pid, path.name)` —— 两条判据：
**pid 等于 rundll32 的 pid**，或**窗口标题里含文件名**。

实测（`tmp_acceptance/probe_chooser_control.py`，只给 pid + 标题，等价于修复前）：

```
[对照] 只给 pid + 标题的调用耗时: 1.04s
[对照] 对话框窗口: ['0x4c0b54']
[对照] 前台: 0x30ABC -> 0x30ABC
[对照] RESULT: 前台是否归对话框 = False
```

同一个探针把窗口信息打出来（`probe_chooser.py`）：

```
新窗口 hwnd=0x194076C pid=71740 proc=OpenWith.exe class='Open With Dummy Window Class For Interim Dialog' title='选取应用'
```

也就是说：真正持有窗口的是 **`OpenWith.exe`**，标题是「选取应用」（英文系统是
「Open With」）—— **pid 不是 rundll32 的，标题里也没有文件名**。两条判据同时落空，
`SetForegroundWindow` 一次都没被调用过；轮询还会白跑满 20×50ms = 1 秒才返回，
于是前端这 1 秒里也没有任何反馈。

「任务栏闪一下」正是「窗口创建了但没被允许成为前台窗口」的标准表现 —— 用户把它读成
「没反应」，是完全合理的。

## 修复方案

三处一起改，缺一处都不完整：

1. **界面：一颗按钮，一个动作。** `SubtitleOpenButton` 去掉右段箭头与 `.split-button`
   包裹层（`frontend/src/styles.css` 里那三条只服务于拆分的规则一并删掉），
   `title` 改为「打开字幕文件；可选择打开方式」，点击直接请求「挑程序」。
2. **接口：缺省就是界面那条路。** `open-subtitle`（任务级 + 条目级）的 `mode` 缺省从
   `default` 改成 `chooser`；前端调用**不带** `mode`，这个决定只写在服务端一处。
   `mode=default` 保留给接口调用方（脚本），文档里标明「界面不再提供」。
3. **置前：多一条「按进程名认领」判据。** `_open_process` 新增 `process_name`，
   `_bring_windows_window_to_front` 在 pid / 标题之外再比进程可执行文件名
   （`_process_image_name`，`OpenProcess` + `QueryFullProcessImageNameW`，只读），
   chooser 传 `OpenWith.exe`。进程名按 pid 缓存，避免每轮枚举都重开句柄。

**为什么不选另一种改法：**

| 备选 | 为什么不做 |
| --- | --- |
| 只修置前，保留两段按钮 | 一个动作仍然有两个入口，其中一个的存在感来自「它以前坏过」。而且「点主段 = 用系统记住的程序」与「点右段 = 当场挑」在界面上无法分辨，tooltip 是唯一的区分物 |
| 一颗按钮 + Shift 点击切模式 | 看不见的入口等于没做（这条本来就是这个控件拆成两段的原因） |
| 前端写死 `?mode=chooser`，服务端缺省不动 | 同一个决定（界面默认用哪种方式）写在两处，改一处就会与另一处不一致；测试也只能钉住前端那一份 |
| 干脆删掉 `mode` 参数 | 会把 `os.startfile` 那条「按文件关联打开」的路径连同 `WinError 1155` 的降级一起变成不可达代码，而它对接口调用方仍然成立。保留参数、改缺省，是范围最小且不留死分支的做法 |

## 效果

| 判据 | 修复前 | 修复后 | 怎么量的 |
| --- | --- | --- | --- |
| 对话框是否成为前台窗口 | **否**（前台 `0x30ABC` 不变） | **是**（前台 = 对话框 `0x194076C`） | `probe_chooser_control.py` / `probe_chooser.py` 读 `GetForegroundWindow()` |
| 调用返回耗时 | 1.04s（轮询跑满仍没找到） | 0.60s（找到即返回） | 同上，`time.time()` 包住调用 |
| 「打开字幕」占宽 | 56px（36 + 20，样式源文计算） | **36.0px**，与相邻图标按钮同宽 | 探针 `getBoundingClientRect()` |
| 四角圆角 | 主段右侧 0、右段左侧 0（拆分痕迹） | `8px × 4`，与相邻按钮完全一致 | 探针 `getComputedStyle().border*Radius` |
| 左边框 | 右段 `border-left: 0` | `1px`，与相邻按钮一致 | 同上 |
| 与前一颗按钮的间距 | 8.0px（到主段） | 8.0px，与「播放 → 文件夹」之间一致 | 探针量相邻按钮的 `right`/`left` |
| 点击发出的请求 | 主段 `?mode=default`、右段 `?mode=chooser` | 只有一条：`/api/jobs/{id}/open-subtitle`（无查询串） | 探针拦截请求并记录 URL |

真机验收：`tmp_acceptance/ui_subtitle_button.py` **24 项断言全通过**（同一脚本在修复前会
在「tooltip = 打开字幕文件；可选择打开方式」「没有残留箭头」「同宽/同圆角」「请求不带 mode」
这几处失败），截图见 `tmp_acceptance/subtitle_button_zoom.png` —— 三颗按钮（播放 / 文件夹 / CC）
形态完全一致，箭头不再存在。

## 验证

**自动化**

- 前端：`task-center-files.test.tsx` 里原先断言「点『选择打开方式 ⬅ 主语』会打到 `?mode=chooser`」
  的用例，改成断言**反向事实**：同一主语下不存在名为「选择打开方式 …」的按钮、`title` 恰为
  「打开字幕文件；可选择打开方式」、并且点击后**只有一条** `open-subtitle` 请求且整条 URL
  与 `/api/jobs/job-running/open-subtitle` 完全相等（带任何查询串都算没走缺省）。
  全量：20 个文件 / 279 条通过；`npx tsc --noEmit` 无输出。
- 后端：`test_api.py` 的 8 条字幕用例（缺省走选择器、`?mode=default` 仍走文件关联且两者是
  不同入口、条目级用自己那份字幕、无字幕 409、未知 `mode` 422、旧记录靠同名文件找到、
  文件没了回 `null`）；`test_system_open.py` 8 条，其中 chooser 那条现在**额外断言
  `process_name == "OpenWith.exe"` 被传下去**（漏传就是这次的 bug 复现）。

**承重（证明断言抓得住缺陷）**

- 置前这条：把 `process_name` 拿掉（`probe_chooser_control.py`），前台窗口不动、耗时 1.04s；
  加回来，前台就是对话框、耗时 0.60s。**同一台机器、同一份 `.srt`、同一个进程调用**，
  差异只来自这条判据。
- 前端这条：新断言是 HEAD 上旧断言（`getByRole("button", { name: "选择打开方式 Running video" })`
  存在且可点）的**精确否定**。旧断言在 HEAD 全绿，说明它钉住的那个元素确实存在；把
  `SubtitleOpenButton` 的箭头加回来，新断言必红。**本轮没有真的做「把旧构建跑一遍探针」**，
  原因见下。

## 风险与回滚

- **行为变化**：按钮不再「用系统记住的关联直接打开」，每次都会弹选择器。勾了「始终使用此应用」
  之后，资源管理器双击、以及接口的 `?mode=default` 仍然用那个程序；只是本按钮不会跳过窗口。
  这是用户明确要求的行为；若日后想两者兼得，正确的做法是**另给一颗按钮**（不是恢复箭头）。
- **`OpenWith.exe` 是 Windows 10/11 的进程名**。更老的 Windows 上窗口可能仍由 rundll32 持有 ——
  pid 判据保留着，两条判据是「或」的关系，不会互相妨碍。macOS/Linux 上 chooser 仍退化成默认打开。
- **多认领一条判据的副作用**：若用户此前已经开着一个 `OpenWith.exe` 的窗口，可能会把那个旧窗口
  提到前台。它本来就是「打开方式」对话框，最坏结果是用户看到一个多余的对话框，不会误开文件。
- **回滚**：三处改动互不依赖，可分别回退；`mode` 参数与 `default` 分支一直保留，回滚界面即可
  恢复旧交互（置前那条修好之后，旧交互也不会再「看起来没反应」）。

## 未覆盖 / 如实说明

1. **「把旧构建跑一遍探针」没做成。** 我尝试把 `frontend/dist/index.html` 临时指向改动前的
   bundle 来复现失败，但那份旧 bundle 在 `frontend/dist/assets` 里已经不在了（构建目录不可信，
   见 `.gitignore` 里的 `dist/`），跑出来是「页面压根没渲染」而不是「渲染出两段按钮」，
   拿到的是 3 通过 / 13 失败 —— **这组数字不能当作证据，故未采用**。前端的承重证据因此是
   「新断言 = 旧断言（HEAD 全绿）的精确否定」这条推理，而不是一次真实回放。
2. **jsdom 量不出形态。** 「同宽 36px / 同圆角 8px / 间距 8px」全部来自 CDP 探针，不进 CI；
   单测能钉住的只有「按钮存在与否」和「请求 URL」。任何一次样式改动都必须重跑探针。
3. **置前这条只在当前这台机器上验过**（Windows 11，Edge/Chrome 前台）。别的 Windows 版本上
   `OpenWith.exe` 的窗口类名与标题可能不同 —— 判据用的是进程名而非标题，按理更稳，但**未在
   其它版本上实测**。
4. **选择器弹出后的一切（挑程序、勾「始终使用」）仍是人工验收**：自动化只证明「请求发对了、
   窗口到了前台」，证明不了用户挑完程序之后系统真的用那个程序打开了文件。
5. **`mode=default` 现在没有界面入口**，只有后端用例覆盖。它是刻意保留的接口能力，不是
   遗留分支；如果将来确认无人调用，应连同 `docs/api.md` 的那一行一起删，而不是留在这里
   慢慢腐化。
