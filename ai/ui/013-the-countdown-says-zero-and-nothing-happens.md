# 013 · 「下一次自动重试 00:00」：到点了却不重试，也不说试过几次

## 现象

投稿完成后，合集与字幕两行都写着 **`下一次自动重试 00:00`**，而且**没有** `已重试 N 次`：

```
合集：等待 B 站视频审核后进行归集   [重试归集]  下一次自动重试 00:00
字幕：等待视频编号                 [重传字幕]  下一次自动重试 00:00
```

用户的两句疑问就是判据：

1. **若 `00:00` 是倒计时，那就该开始重试了** —— 为什么不动？
2. **若已经重试过，下一次也不该是 `00:00`，而且该把次数写出来。**

## 原因

两个缺陷叠在一起，一个在**时钟**，一个在**文案**。

### 一、`next_attempt_at` 是「不早于」，不是「此刻就去问」

`register()` 登记新目标时把 `next_attempt_at` 填成**现在**（`utc_now()`）。这没有错：它的语义是
「已经到期，随时可以问」。真正去问要等调度器下一轮 **扫库**。

而扫库节奏与「问平台的间隔」**共用同一次 sleep**：

```python
# 修复前（bili_auto_retry._sleep_one_round）
interval = max(float(self.policy.interval_seconds), POLL_SLICE_SECONDS)
...
```

`interval_seconds` 默认 60 秒 ⇒ 登记之后要**睡满一分钟**才扫第一次。于是界面在这一分钟里
忠实地渲染「距 next_attempt_at 还有 0 秒」，也就是 `00:00` —— **一个到点却不会发生任何事的时刻**。
把间隔调到 300 秒，这个空窗就是五分钟。

### 二、`attempts === 0` 时那一段文案整个不渲染

```tsx
// 修复前
{retry.attempts > 0 && ` · 已尝试 ${retry.attempts} 次`}
```

于是「**一次都还没试过**」这件事在界面上不可见 —— 而它正是 `00:00` 那个疑问的另一半：
用户无法区分「试过了、在等下一轮」与「还没轮到它」。

## 修复

### 1. 扫库节奏与轮询间隔分开

```python
#: 扫库的节奏（秒）。**它与 `interval_seconds` 是两件事**：
#: 后者决定「同一个目标多久被问一次」（退避的基数），这里决定「多久看一眼有没有到期的」。
SWEEP_SECONDS = 5.0

def _round_seconds(self) -> float:
    return max(POLL_SLICE_SECONDS, min(float(self.policy.interval_seconds), SWEEP_SECONDS))
```

- 扫库只查本地那张小表（`bili_auto_retry`），**不发任何平台请求** ⇒ 5 秒一次可以忽略。
- 每个目标**多久被问一次**仍由 `next_attempt_at` 决定（退避的基数没变）。
- 间隔比 5 秒还短时按间隔睡 —— 没有理由比「每问一次平台」醒得更勤（设置面板的最小值是 10 秒，
  这一条是防御性的）。

### 2. 「到点」单独成一档文案，且次数每档都写

| 状态 | 文案 |
| --- | --- |
| 还有时间 | `下一次自动重试 00:35 · 已重试 1 次` |
| **到点了、还没轮到它跑** | `即将自动重试 · 已重试 1 次`（0 次时写 `还没重试过`） |
| 正在问平台 | `正在自动重试（第 2 次）…` |
| 已完成 / 试够了 | 结果（不变） |

- **不再出现 `00:00`**：一个「倒计时归零但什么都没发生」的数字，比没有数字更容易让人误会。
- `已重试 N 次` / `还没重试过` **每一档都写**：它回答「到底动过没有」。
- `running` 那一档写的是「第 `attempts + 1` 次」：`attempts` 是**跑完才加**的，
  所以正在跑的就是第 N+1 次（跑完那一瞬间界面会变成「已重试 N+1 次」）。

判据收在两个纯函数里（`BiliAutoRetryNote` 导出 `attemptsLabel`，倒计时格式在 `formatCountdown`），
组件只负责按状态选一句。

## 效果

真实浏览器（`tmp_acceptance/probe_bili_retry_due_now.py`，10 条断言全过）：

| 场景（`attempts` / `next_attempt_at`） | 修复前 | 修复后 |
| --- | --- | --- |
| 0 / 已过去 5 秒 | `下一次自动重试 00:00` | `即将自动重试 · 还没重试过` |
| 1 / 已过去 5 秒 | `下一次自动重试 00:00` | `即将自动重试 · 已重试 1 次` |
| 0 / 还有 35 秒 | `下一次自动重试 00:35` | `下一次自动重试 00:34 · 还没重试过` |
| 1 / 还有 2 分钟 | `下一次自动重试 02:00` | `下一次自动重试 01:59 · 已重试 1 次` |

扫库从「每 interval 一次」变成「每 5 秒一次」之后，第一条那种状态**最多持续 5 秒**就会转入
`running` 或「已重试 1 次 + 新的倒计时」。

| 层 | 用例 | 钉住什么 |

| 后端（+1） | `test_the_sweep_cadence_does_not_follow_the_poll_interval` | 间隔 300 秒时一轮仍是 5 秒 |
| 后端（改） | `test_a_shortened_interval_takes_effect_mid_sleep` | 300 → 2 秒，这一轮 2 秒收尾（分段睡） |
| 组件（+3） | 到点 0 次 / 到点 1 次 / 还有时间 | 不写 `00:00`；两种次数都写出来 |
| 组件（改） | 正在问平台 | 「第 2 次」（`attempts=1`） |
| 纯函数（+2） | `attemptsLabel` | 0 → 「还没重试过」；负数按 0 |

承重：把 `_round_seconds` 退回 `interval_seconds` ⇒ 扫库用例红（一轮 300 秒）；
把 `00:00` 那一档改回去（`seconds > 0 ? … : formatCountdown(0)`）⇒ 到点两条红。

## 未覆盖 / 如实说明

- **没在真实平台上跑到「审核通过」那一刻**：`next_attempt_at` 的推进是合成读模型 + 单测覆盖的。
- **关掉自动重试开关后残留的等待行**：`tick()` 直接返回 0，那一行会停在「即将自动重试」不再前进。
  读模型里没有全局开关这一位，所以界面无法说「自动重试已关闭」。这是**已知的边界**，
  比原来的 `00:00` 少一层误导（至少它不再声称一个正在倒数的时刻），但仍不是完整答案。
- **多个目标同时到期时**：一次 `tick()` 只处理一条（平台的账号级频控），排队的那些会持续显示
  「即将自动重试」。5 秒一轮意味着 10 个目标大约 50 秒排完，没有专门的用例量这一串。
