# 头脑风暴：功能候选池（brainstorming）

本文件是 **cascade（yt-dlp 下载控制台）的功能候选池**：记录「接下来值得改进或新增什么」，以及每一条是**凭什么**被提出来的。

它不是实施计划。条目一旦决定做，就在 [`plan.md`](plan.md) 里按「时间戳 + 计划名」另起一节写实施方案，并回到这里把状态改成「已立项（→ plan.md §…）」。

---

## 1. 记录规则

| 规则 | 内容 |
| --- | --- |
| 时间戳格式 | `YYYY-MM-DD HH:mm`（本地时间 +08:00）。**每次头脑风暴都要在 §2 追加一条**，写明当次主题。 |
| 条目编号 | `<分类>-NN`，只增不复用；否决的条目保留编号并写「已否决 + 理由」，不删除。 |
| 条目状态 | `候选` / `待取证` / `已立项` / `已实现` / `已否决`。 |
| 进度标记 | 每条的第一个列表项是**复选框**：`- [x] **已完成**`（附落地记录链接）表示已落地；`- [ ] **未完成**` 表示仍待处理，后面紧跟它的 `状态`。**待办清单就是** `grep '^- \[ \]' ai/plan/brainstorming.md`，不必再维护第二份。 |
| 每条必填 | **现状（含 `文件:行` 依据）**、**痛点**、**建议**、**判据（为什么属于本项目）**、**优先级**、**风险与不做什么**。缺依据的条目不进池。 |
| 优先级含义 | `P1` 有已观测的损害或明确缺口，下一轮就该做；`P2` 值得做、成本可控；`候选` 证据不足或依赖前置，先别动手。 |
| 分工 | 功能坏了 → [`ai/bug-fix/`](../bug-fix/README.md)；界面不对 → [`ai/ui/`](../ui/README.md)；性能根因 → [`ai/perf/PLAN.md`](../perf/PLAN.md)；重构 → [`ai/refactor/`](../refactor/refactor.md)。本池只收**「现在没有、但应该有」**的东西，以及**「有开关但没实现」**这类名实不符的缺口。 |

### 选题闸门（三问，全过才进池）

1. **它服务于本项目的场景吗？** 本机单用户、YouTube 下载、可选的 B站 投稿。三条之外的需求一律不进。
2. **它解决的是已观测到的问题吗？** 依据必须是下列之一：生产数据、故障记录、`文件:行` 的代码事实、可复现实验。凭「别的下载器都有」不算依据。
3. **它是一次可交付的改动吗？** 单个模块 + 一次验收能完成。需要新架构、新进程、新存储形态的，先拆到能一次交付为止。

> 反面教材：本项目已有一次教训 —— 界面上有 `aria2c_connections`、单视频并发等控件，但默认关闭 + `--min-split-size` 使「开了也没变化」是预期行为（见 [`ai/ui/README.md`](../ui/README.md) 与 `docs/technical.md`）。**控件存在 ≠ 功能存在**，本池专门收这类缺口。

## 3. 首轮的总体判断

功能面已经相当完整（FR-1~FR-27 覆盖了解析、下载、任务、诊断、B站 投稿全链）。因此**首轮不建议做「大功能」**，缺口集中在四类：

1. **名实不符**：开关/文案承诺了、实现没跟上（`notify_on_complete`、并发是否实时生效、重启语义）。
2. **可靠性缺口**：进程重启后孤儿任务永不恢复（**已落地，见 D-01**）、删任务不连带删投稿记录 —— 两者都是**存储面损伤**，界面上看不见。
3. **被卡住的验收**：媒体流从未在真实环境验收通过（403），导致所有速度类结论都无法判定。
4. **输入与产出形态的自由度**：模式只有三种（缺音频）、文件名模板写死、playlist 条目只能逐个勾选。

按这个顺序排优先级：**先补名实不符与可靠性，再打通验收，最后才谈新形态。**

## 4. 功能候选池

### A. 解析与选择（输入侧）

#### A-01　非 YouTube 链接：明确拒绝，而不是给出莫名报错
- [ ] **未完成** · 状态：候选　优先级：P2
- 现状：`POST /api/analyze`（`backend/app/routers/analyze.py:16`）不做任何站点校验，直接交给 yt-dlp；而本项目的下载策略（anti403 profile 链、PO token、分辨率档位、`yt-dlp` 的 `youtube*` 提取器假设）**全部是 YouTube 专属**（`backend/app/ytdlp_service.py:52` 的 profile 链、`ytdlp_formats.py:9` 的选择器）。
- 痛点：用户拿 bilibili / 抖音 / 播客 RSS 的链接进来，会得到一句与 YouTube 策略无关的 yt-dlp 报错，排障手册里查不到。
- 建议：解析入口加一次轻量站点判定 —— 非 YouTube 域直接返回「本工具只支持 YouTube」的明确错误；YouTube 域下的非视频链接（频道、首页）沿用现有处理。
- 判据：项目名与全部策略都是 YouTube 专属；**不做站点泛化**（见 §5），但至少要拒绝得体。
- 风险：正则漏判会误伤 `youtu.be`、`music.youtube.com`、`youtube.com/shorts`。实施时以 `yt-dlp` 的 `extractor_key` 判定优先于 URL 正则。

#### A-02　playlist 条目：支持按序号范围 / 关键词过滤 / 反选
- [ ] **未完成** · 状态：候选　优先级：P2
- 现状：`AnalysisPanel.tsx:25-34` 只有「全选 / 清空」+ 逐条勾选；`CreateJobRequest.playlist_items`（`schemas.py:63`）后端已支持任意序号列表，即**后端能力在、前端入口缺**。
- 痛点：几百条目的 playlist 想选「第 20~60 条」只能点 41 次。早期 `plan.md` 已把「按序号范围选择」列为目标，未落地。
- 建议：在选择区加一个输入框，支持 `1-20,35,40-` 语法，解析后与勾选态合并；再加一个按标题过滤的搜索框（过滤的是显示，不是选择）。
- 判据：playlist 是 FR-2 的一等场景；后端已支持，改动集中在前端。
- 风险：范围语法与勾选态的合并规则要写清（是「追加」还是「替换」），否则又是一处名实不符。

#### A-03　字幕语言的默认值与该视频的可用语言不一致
- [ ] **未完成** · 状态：待取证　优先级：P1（取证后可能转入 `ai/bug-fix/`）
- 现状：`applyAnalysisResult()` 每次解析都把语言重置为设置默认值（出厂 `["en"]`），若该视频没有 `en` 轨，标签会显示「已选 1 项：en」而列表里没有对应复选框 —— 用户**无法摘掉**它（[`ai/ui/README.md`](../ui/README.md) 候选 1，已实测复现）。
- 痛点：用户会带着一个自己不想要、且无法取消的语言提交任务。
- 建议：**先取证下游影响** —— 带着不存在的语言提交后，后端是忽略、跳过还是失败（`ytdlp_service.py:516` 附近）。三种结论对应三种处理：失败 → 记入 `ai/bug-fix/`；静默忽略 → 前端把选择收敛到可用语言集合；跳过 → 补文案说明。
- 判据：它同时是界面问题与数据正确性问题，取证前不能定方案。

### B. 下载内容与产物形态

#### B-01　增加「仅音频」模式
- [ ] **未完成** · 状态：候选　优先级：P2
- 现状：`DownloadMode = video_subtitles | video_only | subtitles_only`（`schemas.py:7`、`models.py:21-24`），**没有音频档**；格式选择器只有 `video-only + audio` 合并这一路（`ytdlp_formats.py:9`）。
- 痛点：讲座、播客、音乐类内容只需要音频；现在必须下载完整视频再自行提取。
- 建议：新增 `audio_only` 模式，走 `bestaudio` + 可选转 `mp3/m4a`（转码依赖 ffmpeg，缺失时明确降级为「不转码」并说明）。音频产物**不提供 B站 投稿入口**（投稿要视频）。
- 判据：音频下载是 yt-dlp 的一等能力，且不需要新依赖（ffmpeg 已是既有依赖）；项目面向「保存内容」而非「保存视频文件」。
- 风险：① 转码参数不能开放给用户（与「不允许传入任意 yt-dlp 参数」的边界冲突）；② 与 `skip_existing`、产物发现（`output_paths.py`，按媒体路径偏好判断）的交互要重新验一遍。

#### B-02　产物命名与目录模板可配置
- [ ] **未完成** · 状态：候选　优先级：P2
- 现状：输出模板硬编码 `%(title).200B [%(id)s].%(ext)s`（`ytdlp_service.py:465`），目录结构由 `output_paths.py` 的发现逻辑反推，**用户完全不可配**。
- 痛点：合集下载后想要 `合集名/01 - 标题.mp4` 这类组织方式，目前做不到。
- 建议：设置里提供一个模板输入（占位符白名单 `{title} {id} {index} {playlist} {ext} {resolution}`），服务端渲染并做严格 sanitize（去路径分隔符、Windows 保留名、长度截断）。
- 判据：下载器用户对文件组织的诉求是直接且高频的；`{index}` 只在 playlist 场景有意义，正好覆盖 「批量下载」这个一等场景。
- 风险：路径穿越与非法字符是安全问题，必须先有 sanitize 再开放；模板变更会影响 `output_paths.py` 的产物发现（`_is_preferred_media_path`）与 `skip_existing` 的命中 —— 这是**最容易被低估的连带面**。

### C. 速度与性能

#### C-01　测速：把「并发调到多少」从猜变成有依据
- [ ] **未完成** · 状态：候选　优先级：P2（依赖 C-03 / D-01）
- 现状：设置里有并发、限速、重试、`aria2c` 连接数，但**没有任何测速**（旧待办「测速功能」未勾）。而 `ai/perf/PLAN.md` §3.3 已实测证明：并发是 **item 级**的，单视频任务并发恒等于 1；并发越高单流越慢。
- 痛点：用户面对并发输入框没有依据，只能试；试完「没变化」又以为功能坏了（这正是 P1-1 那条文案修复的由来）。
- 建议：加一次轻量测速（下载固定大小的一小段媒体流，测出单流吞吐），输出一句可执行建议，例如「单流约 X KB/s：建议并发 ≤ N；单视频任务建议启用 aria2c 多连接」。
- 判据：**测速本身不提速**，它的价值是替代猜测；且与既有结论（并发的语义）强耦合，是同一类问题的延续。
- 风险：测速请求本身也算请求，可能触发限流 —— 必须低频、可手动触发、不自动跑。

#### C-02　速度显示口径：任务级速度是否等于在跑条目速度之和
- [ ] **未完成** · 状态：待取证　优先级：P2
- 现状：旧待办提出「显示速度仪表盘；playlist 的速度显示好像并不是该合集内单视频下载速度之和？（包括平均速度）」——**至今没取证**。
- 建议：先读 `transfer_stats.py` 与 `job_read_model.py` 的聚合口径，用一次 3 条目并发任务实测对照（任务级速度 vs 各 item 速度之和）。结论若是口径错误 → 转 `ai/bug-fix/`；若只是展示缺失 → 再谈仪表盘。
- 判据：错误的速度数字比没有数字更糟；它直接影响用户对「并发有没有用」的判断。

#### C-03　运行时参数是否真的即时生效
- [ ] **未完成** · 状态：待取证　优先级：P1（取证优先于实现）
- 现状：FR-10 承诺「并发、限速、重试即时保存；限速/重试变更会让当前视频断点续传重启以应用新参数」。旧待办追问「并发度、限速、重试次数可以实时调整、即可生效吗？」，**未回答**。
- 建议：逐个参数实测一次（改设置 → 观察在跑任务的 opts），把结论写进 `docs/user-manual.md`；与承诺不符的按 A-03 同款处理（要么改实现，要么改文案）。
- 判据：这是典型的「承诺了但没验」；属于本池 §3 第 1 类缺口。

### D. 稳定性与自愈

#### D-01　进程重启后，孤儿任务永不恢复
- [x] **已完成**（2026-10-18 · [`ai/bug-fix/015`](../bug-fix/015-orphan-items-never-resume.md)）　优先级：~~P1~~
- 现状（修复前）：`ai/perf/PLAN.md` §8 附带发现：生产库中存在 **332 个 `queued` + 3 个 `running`** 的历史 item，进程退出后不会自动重新入队，重启后表现为「任务永远排队」。代码中只有 `item_requeued` 这一事件类型（`job_manager.py:684`），**没有启动时的孤儿扫描**。
- 痛点：用户重启应用后看到一批永远不动的任务，只能手动删。这是数据面损伤，且**界面上看不出原因**。
- 建议：启动时扫描 `queued` / `running` 的 item，按策略处理（重新入队 或 标记为 `cancelled`），并在任务行写明「因上次退出被标记为…」；策略做成设置项，默认保守（`cancelled`）。
- 判据：有生产数据（332+3）与明确的代码事实，不是想象出来的需求。
- 风险：① 在途 `.part` 文件能否续传要验，不能续传就必须清理残留；② 重启瞬间可能有并发写库，扫描要在 worker 启动**之前**完成。
- **落地情况（2026-10-18）**：新增 [`orphan_recovery.py`](../../backend/app/orphan_recovery.py)（L2），
  [`JobManager.recover_orphaned_work()`](../../backend/app/job_manager.py) 在 lifespan 里
  **先改库、再 `start()`** —— 风险 ② 用「worker 还没起来」直接消掉，而不是加锁。
  `paused` 条目保持暂停；有已取消条目的任务视为「正在被取消」并整体取消（`cancel()`
  对运行中任务只在内存里记一笔，进程一退就没了，判据必须落回库里）。
- **与建议的偏差及理由**：① 默认策略取 **`resume`** 而不是保守的 `cancelled` —— 下载**幂等且可续传**
  （`continuedl=True`），重排队最坏只是多下一遍，而标记失败要用户逐条点「重启」才能恢复，
  正是本条的痛点；B站 上传选「折成失败」的理由（重投产生重复稿件）在下载侧不成立。
  ② 策略只做成**环境变量**（`YTDL_ORPHAN_RECOVERY`），不进设置界面：它只在「已经崩过一次」之后才有意义，
  平时是个没人会去找的开关；`fail` 留作逃生阀并写进文档。
  ③ 风险 ① 用真实下载验收：人造「只留半个 `.part`」的现场后重启，成品字节数与基准一致、`.part` 被清掉。

#### D-02　连续失败时的队列级退避
- [ ] **未完成** · 状态：候选　优先级：P2
- 现状：失败处理是 **item 级**的 profile 链重试（`ytdlp_service.py:323-350`，5 个 profile）；整批连续 403 时，队列仍以满并发继续冲。生产数据：已结束项 141/213（66%）是媒体流 403/重置（`ai/perf/PLAN.md` §2.3）。
- 痛点：被限流时，重试本身就是放大限流的动作；用户看到的是一排同时失败。
- 建议：滑动窗口统计近期失败率，超阈值自动降并发（或暂停队列），并**显式**提示「已因连续失败暂停，点此继续」——可见、可手动恢复是硬要求。
- 判据：与既有 403 治理（P1-3 的 cookies 提示、profile 链）是同一条线，只是从 item 级升到队列级。
- 风险：自动暂停若不可见，会被当成「应用坏了」；自动降并发若不可恢复，等于把设置架空。

#### D-03　YouTube 限流文案（`rate-limited … for up to an hour`）进入建议库
- [ ] **未完成** · 状态：候选　优先级：P2（成本极低）
- 现状：旧待办最后一条记着这句原始报错；`error_advice.py` 中未见该模式（该文件当前只有 `next_steps` 的渲染逻辑，无任何 `rate`/`limit` 匹配）。

- 判据：项目的硬要求是「新增失败路径必须给出可执行的下一步」（`docs/requirements.md` 验收口径）。

#### D-04　浏览器导入 cookies 的路径收缩
- [ ] **未完成** · 状态：候选　优先级：P1
- 现状：`ai/perf/PLAN.md` §9.2-B 实测：本机 Edge 的 YouTube cookies 全部是 v20 app-bound 加密，离线解密必失败；CDP 回退路线曾**清空真实 cookie 库（53 → 0）**（见 [`ai/bug-fix/005`](../bug-fix/005-edge-cdp-fallback-touches-the-live-profile.md)）；且 `taskkill /IM msedge.exe /F /T` 会杀掉用户全部 Edge 进程（[`ai/bug-fix/README.md`](../bug-fix/README.md) 遗留 2）。
- 痛点：界面上有一个「从浏览器导入」按钮，在本机结构上**必然失败**，且失败路径带数据破坏风险。
- 建议：把主路径明确为「浏览器扩展导出 cookies.txt」，UI 给出分步指引；对不可用的路线降级为明确不可用的提示（或直接移除），避免用户点了才知道。
- 判据：**按钮存在但必然失败**是本池 §3 第 1 类缺口的极端形态，且涉及用户数据安全。

#### F-01　删除任务时连带处理投稿记录

#### F-04　「稿件已在合集中」判成功

#### H-01　`notify_on_complete` 是一个没有实现的开关
- [x] **已完成**（→ [`ai/bug-fix/014`](../bug-fix/014-a-dead-notify-switch.md)）　优先级：~~P1~~

- 建议：二选一 —— ① 实现（前端 Notification API / 系统通知，任务终态时触发）；② 撤掉开关。不允许继续挂着。
- 判据：本池 §3 第 1 类的教科书案例；一个不生效的开关比没有开关更糟（用户会以为通知坏了）。
- 风险：浏览器通知需要权限申请，被拒时要给出明确说明而不是静默失败。
- **落地情况（2026-10-18）**：取了 ①，但**没有用** Notification API —— 权限被拒时的静默失败
  正是上面那条风险。实现拆成两层：全局设置 `completion_notification`
  （`off` / `sound` / `toast` / `both`，默认 `both`）管**用什么方式**，
  逐任务 `notify_on_complete`（默认改为 `true`）管**要不要**。提醒在浏览器里发生：
  提示音由 Web Audio 现场合成（没有音频文件入库），浮层是右下角 DOM、约 6 s 自动缩回、
  悬停暂停、**标签页在后台时不倒计时**。后端只存偏好，并把逐任务开关从 `options_json`
  派生进 `JobRead`（不抬出来，刷新页面就丢）。
- **与建议的偏差及理由**：建议里只有「通知」一种形态，实际给了四种取值 ——
  「声音还是弹窗」是偏好而不是实现细节，写死一种等于替用户决定。

## 5. 明确不做（边界）

| 不做 | 理由 |
| --- | --- |
| 站点泛化（bilibili / 抖音 / 播客等下载） | 下载策略（anti403 profile、PO token、分辨率档位）与投稿链路都是 YouTube 专属；泛化会让策略失真。只做 A-01 的「拒绝得体」。 |
| 开放任意 yt-dlp 参数 | `docs/requirements.md` 约束与边界已写明：API 只暴露项目定义的安全选项。 |
| DRM / 会员 / 地区 / 年龄限制绕过 | 同上，且是法律与安全红线。 |
| 多用户、权限、公网部署 | 项目定位是本机单用户工具。 |
| 视频编辑、剪辑、片段下载 | 与「下载 + 可选投稿」无关，会引入全新产品线。 |
| 云端同步、远程下载机、移动端 App | 引入新进程与新存储形态，与「一次可交付」闸门冲突。 |
| 自动无人值守下载（定时抓取频道更新） | 与 YouTube 限流治理相悖（D-02 正在降低请求频率，定时抓取会抬高它）。 |
| B站 定时发布 / 互动数据运营 | 投稿链路的目标是「把已下载的内容发上去」，不是运营工具。 |
