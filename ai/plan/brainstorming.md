# 头脑风暴：功能候选池（brainstorming）

本文件是 **cascade（yt-dlp 下载控制台）的功能候选池**：记录「接下来值得改进或新增什么」，以及每一条是**凭什么**被提出来的。

它不是实施计划。条目一旦决定做，就在 [`plan.md`](plan.md) 里按「时间戳 + 计划名」另起一节写实施方案，并回到这里把状态改成「已立项（→ plan.md §…）」。

---

## 1. 记录规则

| 规则 | 内容 |
| --- | --- |
| 时间戳格式 | `YYYY-MM-DD HH:mm`（本地时间 +08:00）。**每次头脑风暴都要在 §2 追加一条**，写明当次主题。 |
| 条目编号 | `<分类>-NN`，只增不复用；否决的条目保留编号并写「已否决 + 理由」，不删除。 |
| 条目状态 | `候选` / `待取证` / `已立项` / `已实现` / `已否决`。 |
| 进度标记 | 每条的第一个列表项是复选框：`- [x] **已完成**`（附落地记录链接）；`- [ ] **未完成**`。**待办清单就是** `grep '^- \[ \]' ai/plan/brainstorming.md`，不维护第二份。 |
| 锚点写法 | 指向代码时**优先写 `文件` + 符号名**（`ytdlp_service.py` 的 `_download_once`），行号只在当次核对过才写。**理由**：2026-10-28 的两次重构（后端分包、前端分目录）让上一轮 24 条里的路径全部失效，行号更是一漂几十行 —— 锚点必须能活过一次重构。 |
| 每条必填 | **现状（含代码依据）**、**痛点**、**建议**、**判据（为什么属于本项目）**、**优先级**、**风险与不做什么**。缺依据的条目不进池。 |
| 优先级含义 | `P1` 有已观测的损害或明确缺口，下一轮就该做；`P2` 值得做、成本可控；`候选` 证据不足或依赖前置，先别动手。 |
| 分工 | 功能坏了 → [`ai/bug-fix/`](../bug-fix/README.md)；界面不对 → [`ai/ui/`](../ui/README.md)；性能根因 → [`ai/perf/PLAN.md`](../perf/PLAN.md)；重构 → [`ai/refactor/refactor.md`](../refactor/refactor.md)。本池只收**「现在没有、但应该有」**与**「有开关但没实现」**这类名实不符的缺口；纯缺陷与纯样式问题在 §7 移交，不占编号。 |

### 选题闸门（三问，全过才进池）

1. **它服务于本项目的场景吗？** 本机单用户、YouTube 下载、可选的 B站 投稿。三条之外一律不进。
2. **它解决的是已观测到的问题吗？** 依据必须是：生产数据、故障记录、`文件:行` 的代码事实、可复现实验。凭「别的下载器都有」不算依据。
3. **它是一次可交付的改动吗？** 单个模块 + 一次验收能完成。需要新架构、新进程、新存储形态的，先拆到能一次交付为止。

> 反面教材：本项目已有两次教训 —— ① 界面上有 `aria2c_connections` 控件，但默认关闭 + `--min-split-size` 使「开了也没变化」是预期行为；② `notify_on_complete` 曾经是个**完全不生效**的开关。**控件存在 ≠ 功能存在**，本池专门收这类缺口。

新功能带来了三类**边界问题**，它们不是缺陷，是「做了一半的语义」：

1. **恢复的边界**：能被恢复了，但没有单实例保护（两个进程会同时恢复、同时写同一个 `.part`），也不分批（一开应用就塞几百条）。
2. **自动重试的边界**：状态机能跑（`waiting/running/done/exhausted`），但落库的 `bili_auto_retry` 只增不减，且删任务时不会被清理。
3. **设置的边界**：`032` 刚证明了「库里改了、进程还用旧值」这一类故障；但**诊断接口无法区分「库里的值」与「进程实际生效的值」**，下一次同类问题仍然要读代码。

## 4. 功能候选池

### A. 解析与选择（输入侧）

#### A-01　非 YouTube 链接：明确拒绝，而不是给出莫名报错
- [x] **已完成**（2026-11-11 · [A-01](../feature/A-01-youtube-only.md)）　状态：已实现　优先级：P2
- 结论：判定分两层，**第一层在发请求之前**。主机名白名单（`youtube.com` 及其子域 / `youtu.be` / `youtube-nocookie.com`，协议 http/https）不合规就直接 400，一次网络请求都不发；拿到页面后再用 yt-dlp 的 `extractor_key` 复核（短链、跳转、代理能让主机名说谎）。
- 文案三段：只支持 YouTube + 链接的站点是什么 + **没有向它发起请求** —— 少了最后一句，用户会去查网络、代理与 cookies。
- 反向判据同样重要：11 条合法形态（短链 / 移动端 / 音乐 / shorts / live / 合集 / nocookie）一个都不能误伤，否则故障表现为「工具坏了」，比原来的报错更难查。
- 验证：`test_analyze_scope.py` 35 条（含「替身一次都没被调用」与 `extractor_key` 两层判定）；后端全量 1428 passed。

#### A-02　playlist 条目：支持按序号范围 / 关键词过滤 / 反选
- [ ] **未完成** · 状态：候选　优先级：P2
- 现状：`frontend/src/download-request/AnalysisPanel.tsx` 只有「全选 / 清空」+ 逐条勾选；`CreateJobRequest.playlist_items` 已支持任意序号列表 —— **后端能力在、前端入口缺**。
- 痛点：几百条目的 playlist 想选「第 20~60 条」只能点 41 次。早期 `plan.md` 已把「按序号范围选择」列为目标，未落地。
- 建议：加一个范围输入框（`1-20,35,40-`），解析后与勾选态合并；再加标题过滤（只影响显示，不影响选择）。
- 判据：playlist 是 FR-2 的一等场景；改动集中在前端。
- 风险：范围与勾选态的合并规则必须写清是「追加」还是「替换」，否则又是一处名实不符。

#### A-03　字幕语言的默认值与该视频可用语言不一致
- [ ] **未完成** · 状态：待取证　优先级：P1（取证后可能转入 `ai/bug-fix/`）
- 现状：`App.tsx` 的 `applyAnalysisResult()` 每次解析都把语言重置为设置默认值（出厂 `["en"]`）；若该视频没有 `en` 轨，标签写「已选 1 项：en」而列表里没有对应复选框 —— 用户**无法摘掉**它（[`ai/ui/README.md`](../ui/README.md) 候选 1，已实测复现，**截至本轮仍在**）。
- 痛点：带着一个自己不想要、且无法取消的语言提交任务。
- 建议：先取证下游影响（后端对不存在的语言是忽略、跳过还是失败），再决定记 `bug-fix` 还是前端收敛选择集。
- 判据：同时是界面问题与数据正确性问题，取证前不能定方案。

#### A-04　解析结果标注「本地已有」，让重复下载前就知道会重下几条
- [ ] **未完成** · 状态：候选　优先级：P2　（本轮新增）
- 现状：判「已有」的能力已经存在 —— `api_support.job_download_dir()`（`backend/app/api/api_support.py:87`）对 playlist 用**同名子目录**、单视频落根目录；`output_paths.discover_existing_output_path()`（`:45`）能按 `source_url` 在目录内找到成品。但**解析响应不带这个信息**，「是否已下载」只在建任务后由 `skip_existing` 静默生效。
- 痛点：重复解析同一个合集时，用户不知道点下去会重下 200 条还是只补 3 条；`skip_existing` 的效果也无从核对。
- 建议：解析后为每个 entry 标一个 `local` 布尔（或「已有 / 无」一列），条目表加一列；单视频在建任务前提示「本地已有同名产物」。
- 判据：判据代码已经写好，缺的只是把它挪到解析阶段呈现；直接服务于「批量下载」这个一等场景。
- 风险：① 200 条 entry 各查一次磁盘，要实测耗时（本地 NTFS 预计毫秒级，但必须量过再开）；② playlist 同名会共享目录，所以「已有」的判定本身就是跨任务的 —— 这与 `skip_existing` 的现有语义一致，不是新引入的。

### B. 下载内容与产物形态

#### B-01　增加「仅音频」模式
- [ ] **未完成** · 状态：候选　优先级：P2
- 现状：`DownloadMode = video_subtitles | video_only | subtitles_only`（`backend/app/contracts/schemas.py`、`contracts/models.py`），**没有音频档**；格式选择器只有 `video-only + audio` 合并这一路（`download/ytdlp_formats.py` 的 `format_selector`）。
- 痛点：讲座、播客、音乐类内容只需要音频，现在必须下完整视频再自己提取。
- 建议：新增 `audio_only`，走 `bestaudio` + 可选转 `mp3/m4a`（缺 ffmpeg 时明确降级为「不转码」）；音频产物**不提供 B站 投稿入口**。
- 判据：音频是 yt-dlp 的一等能力，不需要新依赖；项目面向「保存内容」而非「保存视频文件」。
- 风险：① 转码参数不能开放（与「不允许传入任意 yt-dlp 参数」的边界冲突）；② 与 `skip_existing`、产物发现（`output_paths._is_preferred_media_path`）的交互要重验。

#### B-02　产物命名与目录模板可配置
- [ ] **未完成** · 状态：候选　优先级：P2
- 现状：模板仍硬编码 `%(title).200B [%(id)s].%(ext)s`（`backend/app/download/ytdlp_service.py:520`），用户不可配；目录结构由 `output_paths` 反推。
- 痛点：合集下载后想要 `合集名/01 - 标题.mp4` 的组织方式，目前做不到。
- 建议：设置里给模板输入（白名单 `{title} {id} {index} {playlist} {ext} {resolution}`），服务端渲染并严格 sanitize（路径分隔符、Windows 保留名、长度截断）。
- 判据：下载器用户对文件组织的诉求直接且高频；`{index}` 正好覆盖批量场景。
- 风险：路径穿越是安全问题，**先有 sanitize 再开放**；模板一变，`output_paths` 的产物发现与 `skip_existing` 的命中都要重验 —— 这是最容易被低估的连带面。

#### B-03　下载完成后校验产物完整性（时长 / 流信息对不上就标出来）
- [ ] **未完成** · 状态：候选　优先级：P2　（本轮新增）
- 现状：预检有计划分辨率（FR-5 的 `prepare_download`），完成事件里有实际分辨率，但**没有「文件是否完整」的判据**；`.part` 残留 + 状态 `succeeded` 的组合在原理上可能（D-01 落地时就用人造的半截 `.part` 验过续传），而界面只信数据库里的状态。
- 痛点：静默的半成品最贵 —— 用户以为下好了，投稿到 B站 才发现时长少一半。
- 建议：任务终态时用 ffprobe 读时长与视频流分辨率，与元数据比对（时长偏差阈值可配，默认 2%）；超差标「疑似不完整」并给「重下这一条」。
- 判据：与项目「用证据说话」的纪律一致（预检、停滞看门狗、发布对账都是同一套做法）；ffprobe 已在依赖探测里（`/api/diagnostics` 的 `ffmpeg` 项）。
- 风险：① 对超长视频 ffprobe 要读文件头尾，成本要量；② 直播回放、拼接源的时长本身就不准 —— 阈值必须可关，不能把「元数据不准」报成「下载坏了」。

### C. 速度与性能

#### C-01　测速：把「并发调到多少」从猜变成有依据

#### D-05　单实例保护：两个进程不能同时消费同一个库
- [x] **已完成**（2026-11-04 · [`ai/bug-fix/036`](../bug-fix/036-two-instances-write-the-same-part.md)）　优先级：~~P1~~
- 结论：启动路径只有端口预检，而 `--auto-port` 会换端口继续起 —— **端口是网络资源，库与 `.part` 是磁盘资源**，换端口对后者毫无保护；两个进程会同时恢复同一批孤儿条目、同时写同一个 `.part`，且没有任何报错。
- 修法：`data/app.instance.lock` 上的操作系统**非阻塞文件锁**（Windows `msvcrt.locking` / POSIX `flock`），在**解析端口之前**取锁，拿不到就打印「已有一个实例在跑（pid/端口）」并退出 2；`--auto-port` 因此绕不过去。用文件锁而不是标记文件：强杀进程不会留下一个永远挡路的文件。
- 两个实测坑：① Windows 字节锁连**读**都禁止 ⇒ 备注（pid/端口）要写在锁区之外（第 1 字节起）；② 对**空文件**锁 1 字节等于锁了长度 0 的区间 ⇒ 取锁前必须先写出第 0 个字节（单元测试的进程内互斥没抓到，真实双进程才暴露）。
- 验证：7 条单测；真实双进程：A 起来后 B `--auto-port` 换端口仍被拒（EXIT=2，消息带 pid/端口），`taskkill /F` 掉 A 之后 C 能正常启动（锁随进程退出释放）。
- 遗留：只有 `python -m app` 这条路加锁（直接 `uvicorn app.main:app` 不经过 `main()`）；两个不同 `data/` 指向同一批下载目录时不保护；SMB 网络盘上的文件锁语义未验证。
- 现状：`backend/app/__main__.py` 只做 `port_available()` 预检，而 `--auto-port` 会在端口被占时**换一个端口继续起**，于是两个进程可以同时连同一个 SQLite、同时恢复同一批孤儿条目、同时往同一个 `.part` 写（[`ai/bug-fix/README.md`](../bug-fix/README.md) 遗留 21 原文）。
- 痛点：修复前也有同类风险（两人同时点同一个下载），D-01 让「启动即恢复」成为自动行为，风险从「偶发」变成「每次双开都会」。
- 建议：启动时对 `data/app.instance.lock` 取独占锁（Windows `msvcrt.locking` / POSIX `fcntl`），拿不到就打印「已有一个实例在跑（pid / 端口）」并退出；`--auto-port` 不得绕过。
- 判据：唯一会**损坏数据**的候选，而且用户完全看不见（没有报错、没有日志，只有 `.part` 坏了）。
- 风险：① 强制杀进程会留下锁文件 —— 必须用**文件锁**而不是「存在即占用」的标记文件；② 用户在两个不同的 `data/` 目录跑两份是合法用法，锁必须跟着 `data/` 走而不是全局。

#### G-03　诊断回显必须是「进程实际生效的值」，不是库里的值
- [x] **已完成**（2026-11-04 · [`ai/bug-fix/035`](../bug-fix/035-diagnostics-shows-the-stored-value.md)）　优先级：~~P1~~
- 结论：诊断此前只读 `AppSettings`，**从没读过 `Setting` 表**，也没区分「库」与「运行态」——`032` 那类「库改了、进程用旧值」的故障没有异常也没有日志，唯一的现场反而在说「配置是对的」。
- 修法：`DiagnosticsRead.settings_effective` 每项给出 `stored` / `runtime` / `differs`，运行值从**真正持有它的对象**读（`YtDlpService` 的字段、自动重试调度器的策略）；自检**不调用** `apply_stored_settings`（否则会把现场抹平再报「一致」）；设置页仅在真有差异时多一条红字，一致时一个字不说。
- 口径：报 `differs` 而不是「需重启生效」—— 差异的成因有两种（别的进程改库 / 某处持有快照），诊断只能证明「两者不同」；这一点写进了 schema 与文案注释。
- 验证：后端 5 条（两项都回显、库改了未加载要标出、只读、旋钮读调度器、布尔按 `"1"/"0"` 比），前端 5 + 2 条；契约闸门与 openapi 同步；全量 1319 / 342 全绿。
- 遗留：只覆盖**有库副本**的配置项（纯环境变量没有 `stored` 可比）；诊断只说哪项不同，不说怎么修。
- 现状：`/api/diagnostics` 回显配置与依赖状态；但 `032` 的故障形态是「库里已是新值、进程仍按旧值跑」，而诊断当时**看不出这个差异** —— 只能读代码才发现配置对象是构造时快照。
- 痛点：这类故障没有异常、没有日志，唯一的现场就是诊断接口。它现在回显的恰恰是「库里的值」，会把人引向「配置是对的」。
- 建议：诊断项标注来源 `runtime`（进程实际持有）与 `stored`（库/文件里的值）；两者不一致时单独报一条「需重启生效」，并在设置页对应项上标出。
- 判据：`032` 是既有证据（同一形状的问题在 `017` 也出现过：状态没到 UI）。这是把一次教训固化成**下一次的第一现场**，成本一个字段。
- 风险：`runtime` 值与 `stored` 值一致时不应产生噪音 —— 只在差异时显示。

#### I-01　vitest 并行跑会静默丢文件，而它仍报「全部通过」
- [x] **已完成**（2026-11-04 · [`ai/bug-fix/034`](../bug-fix/034-vitest-drops-test-files-when-parallel.md)）　优先级：~~P1~~
- 结论：**根因不是「vitest 不可靠」**——本机 fs shim 对转译缓存的**并发写**回 `EPERM`，module runner `fetch` 失败 ⇒ 该文件的模块取不到、**从未被收集**；汇总行的 `passed` 只统计跑了的那些。三次并行丢的不是同一批（24 文件/255 条、23 文件、24 文件/212 条）。
- 修法：`npm test` 默认 `--no-file-parallelism`；新增 `npm run test:counts`（自己串行跑一遍，拿 JSON 报告把**实跑文件集合**与磁盘 `src/**/*.test.{ts,tsx}` 做集合比较，少一个就退出 1）；配置本身由 `src/test/test-runner.test.ts`（3 条）钉住。
- 验证：串行 26 文件 / 335 条全绿、tsc 0；核数闸门串行 26/26 通过、加 `-- --parallel` 时打印缺失文件清单并退出 1（实测丢了 `bili-upload.test.tsx` 与 `task-center-files.test.tsx`）。
- 遗留：核数只保证「文件都跑了」，文件内被 `skip` 的用例不在比较范围内；串行比并行慢约 2.5 倍。
- 现状：同一条 `npx vitest run --environment jsdom` 连续运行，实测得到 **21 文件/286 条、20/275、19/261、15/172** 四种结果，**全部报 passed**：被丢掉的用例不会失败，只会消失。加 `--no-file-parallelism` 后稳定 21/286（遗留 25，2026-10-28 实测）。
- 痛点：这不是某条用例的问题，是**闸门本身**的问题 —— 它让「测试全绿」这句话在任何一次运行里都可能不成立，包括用它当验收依据的那一刻。
- 建议：`package.json` 的 `test` 脚本默认加 `--no-file-parallelism`（或固定 `--maxWorkers=1`）；并在测试文档里写明「核数必须报文件数 + 用例数，不接受只报 passed」。
- 判据：影响的是所有后续工作的可信度，优先级高于任何单条功能。
- 风险：串行会变慢（21 文件 286 条实际耗时需实测；若代价过高，退而求其次：CI 里串行、本地并行但强制核数）。
