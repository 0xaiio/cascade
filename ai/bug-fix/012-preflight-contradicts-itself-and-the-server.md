# 012 · 投稿表单的本地预检有两处口径不对：列表还在读就要求用户去选合集、标签回显截断写死 12 个字

- **状态**：已修复
- **发现方式**：给新抽出的纯函数模块补单元测试（`frontend/src/biliForm.test.ts`），一条断言当场红
- **提交**：本次提交（hash 见索引，按目录约定下次触碰时回填）

> **为什么不记在 `ai/ui/`**：那条目录的硬要求是「元素 + 属性 + 像素差 + 量它的命令」，
> 收的全是版式/对齐/溢出这类**几何**问题。本条两个格点都不涉及几何：一个是文案列表里多了一句
> 自相矛盾的话，一个是**文案里回显的字数**与服务端不一致。判据按 README——「有失败用例」→ 记这里。

## 问题

两张截图能说清，但都发生在**用户点提交之前**，所以没有报错、没有失败、没有数据被破坏 ——
它只是把用户往错的方向推：

**（一）合集列表还在读的时候，表单同时说两句互相否定的话。**

用户选「加入已有合集」之后、列表还没回来之前的这一瞬间，提交区上方是：

```text
正在读取账号里的合集…
选了「加入已有合集」但还没选是哪个合集
```

而就在它下面的下拉框位置上，还写着第三句「正在读取账号里的合集…」（`BiliUploadDialog.tsx`
的 `{!seasonsLoaded ? <p className="hint">正在读取账号里的合集…</p> : …}`）。
第一句说「还没读完」，第二句就断定用户漏选了 —— 而**那时用户根本没得选**。

**（二）同一个超限标签，弹窗里回显的字数和服务端 400 里回显的字数不一样。**

用户填一个 25 个字的标签时：

| 出处 | 实际文案 |
|---|---|
| 弹窗的本地预检 | `「一二三四五六七八九十十一十二…」这个标签有 25 个字，单个标签最多 20 个字` |
| 服务端 `bili_meta.validate` 的 400 | `「一二三四五六七八九十…（到第 40 个字）」这个标签有 25 个字，单个标签最多 20 个字` |

同一条问题、同一句话，两处截断到**不同长度**（12 与 40）。

## 原因

都在同一个函数上 —— 原先内联在 `BiliUploadDialog.tsx` 里的 `localProblems` useMemo，
本轮重构成纯函数 `frontend/src/biliForm.ts#L133` 的 `localPreflight`。两处都是**独立可达**的，
叠在同一个函数里：

**（一）「正在读取」与「还没选」是两条并列的展开条件，彼此不知道对方存在。**

`git show HEAD:frontend/src/components/BiliUploadDialog.tsx`（第 189-199 行原文）：
两条 `...(cond ? [...] : [])` 各自独立求值，`groupMode === "existing"` 时两条同时成立：

- `!seasonsLoaded` → 第一条出「正在读取账号里的合集…」；
- `!chosenSeason` → 第二条也成立（列表没回来时 `chosenSeason` 必然是 `undefined`）。

后一条本来还有一条二级判据（`seasonId === null` 说「还没选」、否则说「已不在列表里」），
所以它**看起来**已经区分了场景 —— 但那个二级判据区分的是「选没选过」，不是「能不能选」。

**（二）回显长度在前端写死 12，而服务端的预览上限是 40。**

服务端 `bili_meta.py#L28` 就有 `TAG_PREVIEW_MAX = 40`，且第 365-366 行**明确写着阈值不能小**：

```python
# 预览上限**必须大于单项上限**，否则「短到能完整显示」这个分支永远走不到
# —— 一个超限的标签至少有 21 个字，而阈值若写成 12，那句 `if` 就是死代码。
shown = longest_tag if len(longest_tag) <= TAG_PREVIEW_MAX else f"{longest_tag[:TAG_PREVIEW_MAX]}…"
```

前端那一行写的是同一个形状、却不是同一个数：

```tsx
longestTag.length > 12 ? `${longestTag.slice(0, 12)}…` : longestTag
```

**12 这个数字正好踩在服务端注释点名的那个坑上**：能走到这一行的标签至少有
`TAG_ITEM_MAX + 1 = 21` 个字 > 12，所以前端那个三元表达式的不截断分支**从未被执行过**
（与 [010](010-unselectable-probe-raise-skips-the-fallback.md) 的失败形状完全同型：
分支写对了，条件写错了 → 整段成死代码）。同时 40 这个值只在服务端的文案里存在，
前端拿不到 —— `BiliLimits` 里当时**没有** `tag_preview` 字段
（`git show HEAD:backend/app/contracts/schemas.py | grep tag_preview` 无匹配），
所以前端即便想对齐也做不到，只能自己编一个。

## 修复方案

**（一）把 `seasonsLoaded` 变成「还没选」那条判据的前提。**

```ts
...(groupMode === GROUP_MODE_EXISTING && !seasonsLoaded ? ["正在读取账号里的合集…"] : []),
...(groupMode === GROUP_MODE_EXISTING && input.seasonsLoaded && !chosenSeason ? [ … ] : [])
```

列表没读出来时只保留第一句。第二句在列表未就绪时既不成立也没有意义 —— 用户还没有可选项。
`seasonsLoaded` 为 `true` 时行为一字未变（已选过但合集被删掉那条分支照旧）。

**（二）把回显长度变成服务端下发的数字，前端不再自己造一个。**

- `schemas.BiliLimits` 新增 `tag_preview: int`，`bili_meta.limits()` 填 `TAG_PREVIEW_MAX`；
- `frontend/src/types.ts` 的 `BiliLimits` 同步加字段（契约检查会拦漏改，见「验证」）；
- `biliForm.localPreflight` 用它，删掉字面量 12：

```ts
const preview = longest.length > limits.tag_preview
  ? `${longest.slice(0, limits.tag_preview)}…`
  : longest;
```

**为什么不做别的**：没有把这两条判据合并成一个「归集状态机」——那会把一条已经能读了十行的
列表变成一张需要另外维护的状态表，而这里的问题只是两个条件之间的依赖没说清。
也没有把前端的预检整个删掉、只留服务端 400 —— 预检的价值就是在输入框旁边当场说话，
删掉它会把「点提交才发现」当成解决方案。

## 效果

| | 修复前 | 修复后 |
|---|---|---|
| 列表读取中选「加入已有合集」 | `["正在读取账号里的合集…", "选了「加入已有合集」但还没选是哪个合集"]` | `["正在读取账号里的合集…"]` |
| 列表已就绪且一个都没选 | `["选了「加入已有合集」但还没选是哪个合集"]` | 同左（未变） |
| 选过的合集已从列表消失 | `["选中的合集已经不在列表里了，请重新选一个"]` | 同左（未变） |
| 25 字标签的回显 | 弹窗截到 12 字、服务端 400 截到 40 字 | 两处都截到 40 字（同一个 `tag_preview`） |
| 前端那个三元的「不截断」分支 | 死代码（超限标签必 ≥ 21 字 > 12） | 可达（标签短于 40 字时原样回显，已有用例覆盖） |
| `BiliLimits` 字段数 | 6 | 7（+`tag_preview`） |

## 风险与回滚

- **（一）的边界**：唯一的行为变化是「列表读取中不再多说一句」。不会有用户原本靠那句话
  才知道要选合集 —— 下拉框位置上的 `正在读取账号里的合集…` 一直在，且列表回来后判据立刻恢复。
- **（二）会让契约多一个字段**：`BiliLimits.tag_preview` 是**只增不改**，前端拿到它的旧响应
  （若真有缓存）会得到 `undefined` → `longest.length > undefined` 为 `false` → 回显不截断，
  退化成「显示完整标签」。这是**降级而非报错**，且本应用的前端与后端同端口同步发版，不会出现。
- **不动的部分**：文案措辞本身没改（标题/简介两条的「超出 N 个字」与服务端的
  「超出 N 个字（上限 M 字）」仍不同 —— 那是**有意的**：界面把上限显示在输入框旁边了，
  再在提示里重复一遍是噪音）。所以本条只对齐**截断长度**这个会直接矛盾的量。
- **回滚**：`git revert <本次 commit>`。回滚后 `BiliLimits` 少一个字段，前端与
  `docs/openapi.yaml` 会一起退回去（三处同步由 `check_api_contract.py` 保证同进同退）。

  它们必须同时成立才谈得上「口径一致」，拆成两次提交只会让中间那次依旧是错的。
