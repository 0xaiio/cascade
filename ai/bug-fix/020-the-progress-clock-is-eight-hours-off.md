# 020 · 上传进度的时间凭空多出 8 小时（Ep 125 报「已提交 7:59:59」）

## 问题

`C++ Weekly - Ep 125 - The Optimal Way To Return From A Function` 上传到 B站，
进度条上的计时是乱的：跑的过程中显示过 `8:00:xx`，跑完显示 **「已提交 7:59:59」**。
实际那次上传只用了 **52 秒**（库里 `elapsed_seconds = 52`）。

## 原因

两个缺陷叠在一起，缺任何一个都不会出现这个症状。

### 1. 根因：跨接口的时间没有时区，而前端按本地时间解析

服务端存的是 **UTC**（`models.utc_now`），但 SQLite 不保存时区，读回来的是
**naive 的 UTC 墙上时间**；读模型原样序列化，于是发出去的是：

```
"started_at": "2026-10-21T10:29:38.727960"      ← 没有任何偏移量
```

而 ECMAScript 规定：**不带偏移量的 date-time 串按本地时间解析**（`Date.parse`）。
本机是 UTC+8，于是 `10:29:38` 被当成 10:29:38 的**本地**时间，比真实时刻早了 8 小时：

```
真实：  10:29:38Z → 10:30:31Z   = 52 秒
解析：  10:29:38 本地(= 02:29:38Z) → 10:30:31 本地(= 02:30:31Z) = 52 秒   ← 若两端同规则
实际：  10:29:38 本地(= 02:29:38Z) → now(本地时刻)                    = 真实 52 秒 + 8 小时
```

实测库里那条记录（`GET /api/bilibili/uploads?job_id=e79d6c06…`）：

```json
{"status": "reviewing",
 "started_at": "2026-10-21T10:29:38.727960",
 "finished_at": "2026-10-21T10:30:31.280768",
 "elapsed_seconds": 52}
```

`elapsed_seconds`（服务端算的）是 52，界面上却是 8 小时 —— **同一个事实，两处相差 8 小时**，
这本身就是最强的证据。

同一个根因还有第二副面孔：`formatDateTime` 原先是把字符串切片直出，于是 UTC 的墙上时间被
当成本地时间摆给用户（本机 18:29 开始的任务显示成「开始 10:29:38」）。

**为什么用例一直绿**：`biliProgress.test.ts` 与 `appFixtures.ts` 里的时间戳**全部**带 `Z`
（`"2026-10-21T03:00:00Z"`），而服务端从来不发带 `Z` 的。测的是一个真实系统从不输出的形状。
判据：**夹具里出现的格式必须与服务端实际发出的格式一致**，否则「测过」等于「没测」。

**为什么契约闸门没拦住**：`docs/openapi.yaml` 里这些字段本来就写着 `format: date-time`
（RFC 3339 要求带偏移量），也就是说实现一直在违反自己的契约；而
`scripts/check_api_contract.py` **只比字段名与路径×方法**，不看格式。

### 2. 附带缺陷：审核期时钟在切换那一刻就冻结

`BiliUploadProgress` 的秒表推进条件写的是 `running`，而进度块在审核期仍然渲染
（判据是 `waiting`）。`reviewing` 时 `running` 已经是 `false`，于是切过去的那一刻
`now` 就停在最后一个 tick 上，**「已提交」永远不再前进**。

这一条正好解释了用户看到的 **7:59:59**：最后一个 tick 的时刻比 `finished_at` 早一秒，
于是 `8 小时 - 1 秒` = `7:59:59`。修复根因后它会变成「停住的 00:00」—— 仍是缺陷，
只是不再刺眼（审核往往要等几分钟到几小时，停住的时钟会被读成「卡住了」）。

## 修复方案

1. **服务端：跨接口的时间一律自带偏移量**。`schemas.py` 新增

   ```python
   UtcDateTime = Annotated[datetime, BeforeValidator(_as_aware_utc)]
   ```

   `JobItemRead` / `JobRead` / `BiliUploadRead` 的 12 个时间字段全部改用它。
   补成 aware 之后 pydantic 自动序列化成 `...Z`，而 `Z` 是 `Date.parse` 唯一能
   可靠识别为 UTC 的形式。**判据：跨接口的时间必须自带偏移量，不让读它的人猜。**
2. **前端：解析收敛到一个函数**。`formatting.parseServerTime()` —— 不带偏移量按 UTC
   解释，带偏移量按偏移量算。`uploadElapsedLabel` 改用它。
   这层兜底是刻意的：**万一将来某处又漏了 `Z`**，退回的是一个能一眼看出的偏差，
   而不是静默的 8 小时谎报。
3. **前端：`formatDateTime` 按本地时区渲染**。原先切片直出，UTC 墙上时间被当本地时间摆。
4. **前端：秒表按「在等」推进**，不按「在跑」。`waiting` 才驱动 `setInterval` ——
   它同时覆盖「刚开始跑」与「刚切到等审核」（后者起点换了，必须重取当前时刻）。

## 效果

| | 修复前 | 修复后 |
| --- | --- | --- |
| Ep 125（真实 52 秒） | `已提交 8:00:52` → `已提交 7:59:59` | `已提交 00:52`（并继续走） |
| 任务中心「开始/结束」 | UTC 墙上时间（本机差 8 小时） | 本地时间 |
| 审核期秒表 | 切过去那一刻冻结 | 按秒继续 |

## 风险与回滚

- **API 的时间戳多了一个 `Z` 后缀**：任何按字符串切片消费它的代码都要跟着改。
  本仓库唯一一处就是 `formatDateTime`（已改成按本地时区渲染）。外部消费者若存在，
  这是一个**行为变化**而不是破坏 —— 带 `Z` 的串本来就符合 `format: date-time`。
- **`formatDateTime` 的显示值变了**（UTC 墙上时间 → 本地时间）。这是修正：显示值必须和
  用户手上的钟一致。唯一的用例已按本地时区改写。
- 回滚：`git revert <commit>`，无数据迁移（列结构没变）。

## 未覆盖 / 如实说明

- **没有在真实浏览器里量过**：Ep 125 那条记录在库里可以复现（接口层已验），但「进度条上
  那行字」的真实渲染没有用 CDP 探针量 —— 本轮的判据是接口返回的串与纯函数输出。
- **`JobItemRead.started_at` 等下载侧时间字段**同样改成了带 `Z`，界面上「开始/结束」的
  显示值随之改变；这一条只被任务中心那条用例间接覆盖，没有专门的时区用例。
- **其它可能也在按本地时间解释时间的代码**（若有）：本轮只查了 `Date.parse` / `new Date(字符串)`
  两类入口，全仓库前端各一处，都已收敛到 `parseServerTime`。
- `checked_at` 是 epoch 秒（绝对时刻），不受这条影响，未动。
