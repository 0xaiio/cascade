# 022 · 「CC 字幕已上传（239 条，en）」—— 239 是什么，以及它为什么不该出现在界面上

## 问题

`C++ Weekly - Ep 130` 发布后，字幕那一行写着：

> CC 字幕已上传（239 条，en），观众可在播放器里开关

用户问的是两件事：**「239 条」是什么意思？这是一个 bug 吗？**

## 答案（先给结论）

- `239` 是这次上传的 BCC `body` 的**段数**（cue 数）。
- **数字本身没算错**：平台侧 `GET x/player/v2` 拿到字幕 JSON，`body` 正好 **239** 条，且与本地逐条
  `from / to / content` **完全一致**（实测见下）。既没被截断，也不是编出来的。
- **但把它写在结论里是缺陷**，三条理由：

| # | 理由 | 判据 |
| --- | --- | --- |
| 1 | 它回答不了任何问题 | 不是字数、不是句数（这份文件 122 句）、也不是「字幕轨数」；它只是转换器的中间量 |
| 2 | 旁边还跟着平台码 `en` | `en` / `zh-Hant` 是发给接口的取值（白名单），界面要求直白中文 |
| 3 | 这个数**虚高近一倍** | 241 条原始 cue 里 **119 条是 10 毫秒过渡条**，它们本该在转换时被丢掉 |

也就是说：**不是一个「算错」的 bug，而是两个缺陷叠在一起** —— 转换留下了噪音（数字虚高），
界面又把内部量当结论说给用户（数字无从解释）。

## 原因

### 1. 滚动字幕的 10 毫秒过渡条没有被丢掉

YouTube 的自动字幕是**滚动**的：一个滚动窗口里放两行，换行时插一条约 10 毫秒的 cue。
这份 `.en.vtt` 的前四块（逐字）：

```
00:00:00.030 --> 00:00:03.050     ← 滚屏条：A
hello<c> and</c><c> welcome</c>…
00:00:03.050 --> 00:00:03.060     ← 过渡条（10ms）：A
hello and welcome to C++ weekly I'm your
00:00:03.060 --> 00:00:05.120     ← 滚屏条：A + B
hello and welcome to C++ weekly I'm your
host<c> Jason</c><c> Turner</c>…
00:00:05.120 --> 00:00:05.130     ← 过渡条（10ms）：B
host Jason Turner I am available for
```

实测这份文件：

```
文件行数: 976        原始 cue: 241
合并同文后: 239      上传的 BCC body: 239（后经平台回读确认一致）
去重后的文字行（句数）: 122
时长 = 0.010s 的 cue: 119，其中 119 条的文字都已被相邻 cue 完整覆盖
首条 0.03–3.05 / 末条 351.3–353.36（全片 5:53）
```

`merge_repeated_cues` 只合并「**整条**内容完全相同」的相邻 cue。滚动窗口里相邻的两条是
「上一行」/「上一行 + 新一行」，永远不相等 ⇒ 过渡条几乎全留（241 → 239，只合掉 2 条）。

**120 条过渡条里为什么只合掉 2 条**：第一对（`A` 与 `A`）文字相同，合掉了；之后每条过渡条的内容
是**新出现的那一行**（`B`），而它前面那条是 `A`+`B` —— 不等于，于是留下。

### 2. 界面把「转换器的中间量」当成结论的一部分

```python
message=f"CC 字幕已上传（{count} 条，{lan}），观众可在播放器里开关"
```

`count` 来自 `load_bcc`（段数），`lan` 来自平台白名单。两个都是**接口/实现细节**。
用户看不懂，也不可能据此判断「字幕是不是完整」—— 而这句话里唯一有价值的信息
（已上传、观众能开关）被两个数字挤到了后面。

## 修复方案

### 1. 转换时丢掉过渡条：`drop_transition_cues()`

```python
TRANSITION_MAX_SECONDS = 0.05          # 实测过渡条正好 0.010s；0.05 是 3 帧，仍不可见

if cue.end - cue.start <= TRANSITION_MAX_SECONDS:
    # 文字必须已被**相邻** cue 完整覆盖
    if _lines_of(cue) and _lines_of(cue) <= neighbour:
        continue
```

**两个条件缺一不可**，各自挡一类误删：

- 只按时长删 ⇒ 会误删「真的只有几十毫秒、但内容独一无二」的短字幕；
- 只按「文字在别处出现过」删 ⇒ 会误删正常重复（同一句话隔几秒再说一次是新的字幕），
  所以判据只看**紧邻的两条**，不是整份文件。

`load_bcc` 的三步定序也固定下来：**解析 → 丢过渡条 → 合并同文**。先丢再合：过渡条的文字就是
上一行，先合并会把它的结束时间并进上一条，之后就再也认不出它是过渡条了。

### 2. 界面只说结果，语言说人话

```
CC 字幕已上传（英文），观众可在播放器里开关
```

- 语言走 `language_display()`：`en→英文`、`zh→中文`、`zh-Hant/zh-TW/zh-HK→繁体中文`，
  认不出来的码**原样回显**（不猜成别的语言）。
- 段数不丢，只是回到它该在的地方：`SubtitleOutcome.cue_count` 与日志
  （`bili 字幕上传完成：… 段数=122`）—— 排障要看的是它，用户不看。

## 效果

同一份 `.en.vtt`（Ep 130）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 上传的段数 | **239** | **122**（= 句数） |
| 10 毫秒过渡条 | 119 条原样上传（换行处闪一帧） | 0 |
| 首条 / 末条时间 | 0.03–3.05 / 351.3–353.36 | 0.03–3.05 / 351.3–353.36（不变） |
| 界面那一句 | `CC 字幕已上传（239 条，en），…` | `CC 字幕已上传（英文），…` |

**全语料校验**（本机 `downloads/` 里全部 28 个 `.vtt`，20,385 条 cue）：

```
28 个文件：原始 20385 → 保留 10973（丢 9412，46%）
被丢但时长 > 0.02s 的 cue：0
落库后仍 <= 0.05s 的 cue：0
末条结束时间被改变的样本：0
文字丢失的样本：0
```

即：**丢掉的全是 10 毫秒过渡条**，没有一条正常字幕被删，没有一句话丢失，字幕覆盖时长一字不差。
（46% 这个比例也解释了为什么「239 条」看起来那么怪：将近一半是噪音。）

## 风险与回滚

- **已在平台上的字幕不会被改写**：这次修复只影响之后的上传。要让那条稿件也变干净，需要点一次
  「重传字幕」—— 字幕重传是**覆盖**，不会多出一条稿件。
- **删除面**：判据是「≤50ms」且「文字被相邻 cue 完整覆盖」。全语料里被删的 9412 条**全部**
  ≤0.02s；想误删得同时满足「极短」与「文字已出现在紧邻处」，正常字幕构造不出这个形状。
- **行数/字数的观感变化**：同一份字幕上传后段数约为原来的 54%，这是修正而不是丢内容
  （文字集合逐字校验无变化）。
- 回滚：`git revert <commit>`。无数据迁移、无接口字段变化。

## 代执行：对已发布稿件重传一次字幕（2026-10-21 23:10）

用户要求代执行。**没有走 HTTP API**：那条链路由常驻后端执行，而后端进程是 21:14 启动的，
`bili_subtitle.py` 是 22:18 改的 —— 它内存里还是旧模块，点「重传字幕」仍会传 239 段。
改为在**新进程**里跑同一条产品代码路径（`reverify` → `_attach_subtitle` → `upload_subtitle`），
结论按 `BiliManager._store_result` 原样落账（用一个只有 `engine` 与 `_progress_lock` 的 shim
复用该方法，不复制字段清单）。

**结果（平台侧逐条回读）**：

```
字幕轨 id: 2134407068567163392（旧，239 段） → 2134441578788466944（新）
body 段数: 239 → 122，与本地新转换逐条一致（from / to / content 全等）
最短一段: 0.010 s → 1.369 s（过渡条已消失）
记录: subtitle_state=posted，message='CC 字幕已上传（英文），观众可在播放器里开关'
```

**三条现场教训**（都不改代码，但要记住）：

1. **先落账、再打印细节**。第一次脚本在 `print(f"… cue_count={result.cue_count}")` 上崩了 ——
   `UploadResult` 没有 `cue_count`（那是 `SubtitleOutcome` 的字段）。字幕**已经传上去了**，
   结论却没落账，只能再跑一次。同一内容重复提交是幂等的，但会多一次处理窗口。
2. **重传后 `player/v2` 会有一段「读不到 / `subtitle_url` 为空」的中间态**。实测：同一个字幕 id
   在连续几轮里时而带 URL、时而为空、时而整条不在列表里（缺的一轮里只有 `ai-zh`）。
   8 轮里 0 轮可读 → 再等两分钟 → 3 轮里 2 轮可读且 body 恒为 122。**判据：拿到 URL 时内容稳定，
   就是缓存/处理中的中间态，不是「字幕被删了」。**
3. **本机 IPv6 到 `api.bilibili.com` 是黑洞**：默认地址顺序下单个请求 64.5 s（SYN 打不通再回落），
   强制 IPv4 只要 0.4 s。第一次执行因此在 `find_archive` 上挂了 8 分钟。这是**环境**事实，
   不是产品缺陷；但任何一次性脚本/探针都该强制 IPv4。

## 未覆盖 / 如实说明

- ~~没有真实重传一次字幕~~ → **已于 23:10 代执行**（见上一节）：平台 `body` 239 → 122 段，
  与本地逐条一致、最短一段 1.369 s。
- **观众侧（未登录）读不到字幕轨**：匿名请求 `player/v2` 的 `subtitles` 为空，登录态能读到。
  这可能是「CC 需要登录态 / 需要 buvid」也可能是「刚提交还在审核」，本轮**没有区分**，
  所以不断言「观众现在就能开关」。
- **换行处是否还闪**没有肉眼验证：只证明那 119 条 10 毫秒的 cue 已不在平台上。
- **「闪一帧」只在数据层确认**：10 毫秒不足 60fps 的一帧，肉眼本来也难判；本轮只证明那 119 条
  的时长与内容，没有做逐帧播放录像。
- **字幕仍然是「滚动窗口」形态**：留下的 122 段里，每段是「上一行 + 新一行」两行。要变成
  「只显示新一行」需要重排时间轴，会改变观感，本轮没做（也不是用户问的问题）。
- **其它语种的滚动形态没样本**：本机 28 个字幕全是英文轨；中文轨（`zh`）的滚动行为未实测，
  不过判据与语言无关。
- 全语料里没有任何「≤50ms 且文字唯一」的 cue，所以「守护用例」保护的场景是构造出来的
  （来自对过渡条形态的理解），不是本机真实样本。
